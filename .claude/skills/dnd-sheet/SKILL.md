# D&D Character Sheet

Alex's from-scratch, single-file D&D 5e (2014 rules) character sheet app — a clean-room replacement for MPMB's PDF sheet, built because MPMB's automation is inseparable from its Adobe/look (reskin proven impossible). The whole app is one self-contained `index.html`: inline CSS + JS, no frameworks, no Adobe or proprietary software required to view it, with the full 5etools sourcebook baked into a `#source-data` `<script>` (~5MB of the ~13MB file) so GitHub Pages serves it self-contained and it works fully offline.

- **Deploy = push to `main`.** Alex runs the GitHub Pages build (`baestheorem.github.io/dnd-character-sheet`), not the local file or stale Drive/iCloud copies. When he says "I don't see my change," the answer is almost always "reload the Pages tab," not a code bug.

## First moves every session

1. **`grep` on `index.html` WILL hit the baked data blob — expect it before your first grep, don't get surprised and redirect.** You read this file by grepping constantly, and ~5MB of WotC JSON lives in the `#source-data` `<script>` as ONE physical line (plus base64 at the `PAGES` line). So `grep -n "<term>"` for anything that also appears in the data (`edition`, `bakedBooks`, `name`, `text`, spell/feature names, common words) prints that whole multi-MB line and overflows the tool output (bare `grep -n "edition"` dumped 19MB once). Two habits: (a) **anchor on code-only tokens** that can't be in JSON — `grep -n "function isBook2024"`, `grep -n "const RULESET_2024"`, `grep -n 'id="loaded-books"'`; (b) when a term might be in the data, **don't print the matched line raw** — `grep -n "term" index.html | awk -F: '{print $1}'` (line numbers only) or `| cut -c1-160`, then `Read` that line range.
2. **Read `VERSION`** (current SemVer) and the top of the in-app changelog before bumping anything. Alex commits in PARALLEL during sessions — a stale assumption about the current version will regress it (I once clobbered 2.32.0→2.31.1). Never assume the last value you set is current; re-read first.
3. **For ANY D&D rules value, read the source data — never use memory.** This is absolute here. My recall of stat blocks, spell dice, level progressions, feature text, DCs, HP formulas has been wrong repeatedly and silently corrupted the sheet (shipped Primal Companion from memory, got passive Perception / HP formula / attack dice / grapple DC all wrong). Pull from `~/My Drive/5etools/data` (override via `FIVETOOLS_DATA`; same path `build-data.py` uses). A server may run at `http://localhost:5050` but is often down — the raw JSON on disk is always there. Key files: `class/class-<class>.json`, `optionalfeatures.json` (FS:*/EI/MV:B/MM by featureType), `bestiary/bestiary-<src>.json`, `spells/`, `races.json`, `feats.json`, `items.json`, `magicvariants.json`. Strip `{@tag ...}` markup when reading. Verify finished work with a programmatic diff against source when feasible.
4. At the end of every change set, follow **"After every change set" below** — auto-commit + push, then update THIS skill with anything new you learned.

## Testing protocol (this matters — read it)

The `<script>`-extract-then-`node --check` syntax check is **UNRELIABLE** on this ~13MB file: a `</script>` literal inside a string truncates the regex extraction (false "Unexpected end of input"); brace-count deltas are noise from strings/regex. A duplicated `function compute(){` once would have shipped a fully-broken sheet and node-on-extracted-script missed it.

**Always verify edits by loading the page in Playwright** and checking `page.on("pageerror")` + `typeof compute === 'function'`. That catches the real breaks. When an Edit looks balanced but the page breaks, `git diff` to spot an accidental duplicated/dropped line (a common cause: an Edit `new_string` that re-includes the trailing context line).

- **`grep` hits the baked data blob** — see First moves #1 (anchor on code-only tokens, or line-numbers-only / `cut -c1-160`); it's the very first thing to internalize because reading this file means grepping it.
- **Playwright = the PYTHON package** (`/opt/homebrew/bin/playwright`, `pip install --break-system-packages playwright && python3 -m playwright install chromium`), NOT Node. Click `#intro-skip` to dismiss the welcome overlay.
- **Do NOT use `--headless=old`** on this file — it renders the whole `<style>` block as visible body text (a headless artifact, not a real bug) and `--dump-dom` can DEADLOCK forever (a render once hung 57 min and froze the whole session). macOS has no `timeout` binary (use `gtimeout` or a `&`+poll watchdog). Prefer the **browser-render skill** for flash-free capture, or Playwright `evaluate()` + `full_page` screenshot. If a render hangs: kill the Chrome chain on `user-data-dir=/tmp/render-e` + `rm -rf` the lock dir.
- **Print-media FULL-PAGE screenshots of this file paint blank/gray bands where content actually exists** (headless paint artifact on the 13MB page, seen 2026-07-02: `#page-core` showed as a blank band while `getBoundingClientRect` proved it laid out with content). Before diagnosing a "blank page in print" bug, take an ELEMENT screenshot (`query_selector('#page-core').screenshot(...)`) or probe layout — the element shot renders fine. Also: the UCS→canonical print fallback listens for a real `beforeprint` event; `emulate_media(media="print")` alone does NOT fire it, so dispatch `new Event('beforeprint')` first when simulating the app's print path. **But there was ALSO a real "Core prints blank" bug (fixed 2.99.1) distinct from the screenshot artifact — don't let the artifact note make you dismiss a genuine report.** Root cause: `_ucsAfterPrint` (bound to BOTH `afterprint` AND `focus`, the focus handler being a Safari/mobile fallback) re-activated the UCS landscape layout whenever `window.__ucsPrint` was set — but a `focus` event FIRES during Chrome's interactive print preview (opening it / changing settings), so mid-print it relocated the just-restored Core cards back into the hidden `#ucs-*` scaffold → `#page-core` printed blank while every other page (whose cards aren't relocated) printed fine. Fix: `_ucsAfterPrint` now early-returns while `matchMedia('print').matches` (still printing), so only a focus/afterprint AFTER print ends restores the dashboard. **Repro headlessly (deterministic, unlike the artifact):** `emulate_media("print")` → dispatch `beforeprint` (Core restored: `ident` card present, 0 `template.ucs-ph` left) → dispatch `focus` → BEFORE the fix, `body.ucs-layout` flips back on and `#page-core` holds only placeholders (`ph:11`, `ident:false`); AFTER, it stays restored. A real `page.pdf()` renders the Core page correctly either way (it doesn't fire the stray focus), so PDF alone won't catch this — the focus-injection unit probe does.
- **Preview a theme** by copying index.html and swapping `const DEFAULT_THEME = "ucs"` → the target theme id, and `let darkMode = prefBool(DARK_KEY)` → `true` for dark.
- **Headless test seams** (things that don't render the way you'd expect): hand-pushed `asiChoices` get wiped by `compute()→syncAsiSlots()` (truncates to `asiCount()`, 0 without a class) — set `#classlevel='Fighter 4'` for a real slot; the ASI panel DOM only renders when its panel is open. Class-resource Limited rows (Arcane Recovery, Channel Divinity, Bardic Inspiration) come from `LIMITED_RESOURCES` via `fillLimitedFeatures(cls,lvl)` at char generation, NOT `refreshLimitedFeatures` — seed them to test. Write-in spell rows hold the name in an INPUT VALUE, not textContent (search `input.sp-name` value). A headless wizard sheet needs `spellMaxByInst[0]=9` + `spellEntriesOf(0)[L]` set to render spell rows.

## Keep app CODE copyright-clean (load-bearing constraint)

Alex may one day **sell or more widely distribute the sheet itself**, so the app code must stay free of copyrighted WotC material. The design rule: **the baked `#source-data` blob is the ONLY place copyrighted content is allowed to live.** Null out `#source-data` and what's left should be a copyright-clean app (point it at a 5etools source to reconstitute). The whole-file-with-data-baked-in is fine for Alex's own use *today*; the separation is what keeps a future strip-and-sell viable.

**What this means for every edit that adds content:**
- Never hardcode copyrightable WotC TEXT into app JS (spell/feature/item/invocation/maneuver/metamagic/fighting-style descriptions, stat-block prose). It belongs in `#source-data`, pulled in by a loader. This is already done — `OPTIONAL_FEATURES` and `FIGHTING_STYLES` text were de-baked into `#source-data` (via `etOptionalFeatures`) so app code is text-free. Keep it that way; don't reintroduce verbatim text into a registry.
- **Names + mechanics + formulas are NOT copyrightable** and are fine to keep hardcoded — that's why the hand-coded registries (`FEAT_SPELLS`, `FEAT_SKILLS`, `FEATURE_ATTACKS`, `LIMITED_RESOURCES`, `ELSEWHERE_ITEMS`) live in app JS and survive a rebake. Alex's OWN paraphrase prose (`SPELL_CHANGES`, `TCE_RULES`) is also fine to keep — it's his words.
- Audit reference: nulling `#source-data` takes the file ~13.3MB → ~2.85MB with a graceful "load a sourcebook" prompt; reload works via a local 5etools server OR a CORS mirror (e.g. the jsDelivr 5etools-2014 mirror). If you add a new content type, route its TEXT through `#source-data` + a loader, not into app code.

### The DATA_VERSION gotcha (causes "Sourcebooks out of date" forever)

When you bump the `DATA_VERSION` const, you **MUST also re-stamp the baked `#source-data` `_meta.dataVersion`** to match. CAREFUL: since 2.85.0 the blob carries MORE THAN ONE `"dataVersion":N` (the top-level `_meta` one, before `"pendingAug"`, is FIRST; per-book raw `_meta` blocks like the baked WGtE carry their own copy later). Re-stamp the FIRST occurrence; a blind replace-ALL also rewrites the book-level copies (harmless today since they match, but verify counts before and after). A const-only bump makes the baked data SELF-STALE; a clobbered stored copy ties-and-wins and the flag shows forever. Because the Edit tool's file-state tracking fights this 13MB file (and SOH `\x01` separators in some sigs can't be matched by Edit at all), use a **verified Python byte-level replace** for these edits, not the Edit tool.

- **Conditions & Exhaustion engine:** Defenses is a subsection inside the Combat card (`.combat-sub`), with a **Conditions** subsection beside it. `CONDITIONS` (app-JS registry: key, name, *paraphrased* rules text = copyright-clean, and an `eff` object) + `EXHAUSTION_STAGES` drive everything. `buildConditionsPanel()` (called in `init()` BEFORE `applyAll` so the `data-save` inputs exist to restore) builds `#cond-panel`: one `#cond-<key>` toggle + expandable rules per condition, plus a 6-pip `#exhaustion` tracker. **`#cond-panel` lives in a popup `#cond-modal` (`.modal`/`.open`)**, opened by the "Manage conditions" button; the conditions-sub only shows the active chips + button. `condEffects()` aggregates active conditions + exhaustion into `{disadv:Set, adv:Set, speedZero, speedHalf, hpHalf, incap}` where adv/disadv tags are `attack`/`check`/`save`/`save:str`/`save:dex`. ## Homebrew Builder (the three-step workflow for fully fleshing out homebrew)

When Alex wants to create homebrew material (a spell, item, and eventually a feat/race/subclass/class/background), drive it through these THREE steps in order. The point is that the finished piece ends up as a portable JSON file that, when imported, gets **first-class mechanical support** on the sheet (auto-applied AC/attack/DC/attunement/etc.), not just stored as inert text.

**Step 1 — Iterate on the material itself, together.** Design it WITH Alex before touching code. Settle the name, the rules text, and (critically) the *mechanics*: what numbers/effects it grants and under what conditions. Ground every rules value in real D&D data (`~/My Drive/5etools/data`) per the absolute "never from memory" rule at the top of this skill. Decide the balance/tier. The deliverable of this step is an agreed spec: exactly what the thing does, in mechanical terms.

**Step 2 — Modify the sheet code to support its mechanics (only if needed).** Check whether the existing homebrew schema + engines already cover the mechanics:
  - A plain **spell** (level/school/components/text/higher) or a **magic item** whose effects are AC bonus / spell-attack bonus / spell-save-DC bonus / attunement / weapon math (Ancestral Weapon) — **no code change needed.** The current homebrew item/spell shapes + the existing overlay functions (`hbActiveItems`/`hbActiveSpells`/`hbEnabledItem`/`acItemMap`/`spellBonusItemMap`/`attuneSet`/`allItemText`, and `awDerive`/`hbAwMagicWeapon` for AW) already auto-apply these. Skip to step 3.
  - A mechanic **beyond** that (a novel rider, a new resource, a feat that grants a skill/attack, a race trait with a special AC formula, etc.) — extend the sheet using the **proven injection recipe** (the same one items + AW follow): store the new field on the per-source object, add/extend a normalizer, and inject an `hbActive<Type>()` (or new field handler) **at that mechanic's resolver read points** — NEVER merge homebrew into `DATA`/`mergeBook` (homebrew is a carried key, not a merged book). For copyright cleanliness, names+mechanics+formulas stay in app JS; verbatim copyrighted TEXT rides `#source-data` (see "Keep app CODE copyright-clean"). Bump SemVer for the code change.

**Step 3 — Encode it as a homebrew JSON file for first-class import.** Author the finished material as a homebrew JSON envelope and import it via the Homebrew Studio's **"Import JSON…"** button (it merges into the *currently selected* source). Because import routes each entry through the same normalizer + storage as the in-app forms, the imported content gets identical first-class treatment. The envelope (shipped 2.67.0):
```json
{
  "_meta": { "homebrew": true, "name": "Source name (optional)" },
  "spells": [ { "name":"…", "level":2, "school":"Evocation", "components":"VS",
               "time":"1 action", "range":"60 feet", "duration":"Instantaneous",
               "material":"", "conc":true, "ritual":false, "text":"…", "higher":"…" } ],
  "items":  [ { "name":"…", "type":"Wondrous Item", "rarity":"Rare", "attune":true,
               "acBonus":0, "spellAtk":0, "spellDc":0, "text":"…",
               "aw":{ … } } ]
}
```
Each content type accepts an **array OR an object map** (`{lowercase-name: obj}`); merge is additive, by lowercased name, last-wins. `components` tolerates 5etools-style `{v,s,m}` (normalized to a `"VSM"` string). An `items[].aw` blob (Ancestral Weapon build) is preserved and round-trips; if present, an **export** also bundles the AW upgrade catalog + text so the file is self-contained. A full **sourcebook**-schema file (`races`/`classes`/`spells` as top-level arrays) is rejected here with a pointer to Settings → Import files… — don't conflate the two import paths.

**Code seam (all ≈ the `importAwContent` neighborhood, before `buildHbStudio`):** `HB_IMPORT_TYPES` is the **single registry** of homebrew content types — `[{key, label, norm}]`, currently `spells` + `items`. `normHbSpell`/`normHbItem` coerce a loose object into the stored shape. `hbImportIntoSource(idx, d)` merges a parsed file into `homebrewSources[idx]` (returns `{counts, total, name}` or `{err}`); `hbExportSource(idx)` writes the selected source out (`download`). `hbAwBundleInto(d)` folds AW upgrade defs+text and is shared by `importAwContent` + the homebrew importer (DRY — don't reintroduce a second copy). UI: `#hb-src-import`/`#hb-src-export` buttons + a hidden `#hb-import-file` in the Studio's `.hb-src-row`, wired in `buildHbStudio`; success/skip is summarized generically from `HB_IMPORT_TYPES` labels.

**Two injection strategies — pick by how the builder reads the type:**
- **Lookup-overlay (spells, items):** the read points go through centralized lookup fns, so overlay enabled homebrew there (`hbActiveSpells`/`hbActiveItems`/`hbEnabledItem`/`spellData` precedence). Homebrew is NEVER put into `DATA`.
- **Merge-into-DATA (feats, races/subraces, backgrounds, subclasses — SHIPPED 2.68.0):** the builder reads these from the live `DATA` arrays in DOZENS of scattered places (race picker + `applyRace`, feat pickers + `applyAsiBonuses`, background picker + `applyBackground`, subclass picker + feature-by-level application), so per-read overlay is impractical. Instead `hbApplyToData()` merges enabled homebrew of these types INTO `DATA.races`/`.feats`/`.backgrounds` and the parent class's `.subclasses` (run through `normalizeSubclass`), each injected entry tagged `_hb`; `bakeSourceData`/`persistSources` strip `_hb` via `hbStripClone` so `#source-data` + the localStorage cache never double them (homebrew always rides `DATA.homebrew`). It's idempotent (`hbStripData` removes prior injections first) and re-run on `refreshAfterData`/`refreshHomebrew`/init-after-`loadHomebrew`. A homebrew subclass needs its **parent class loaded** to attach; subraces fold into parents via `resolveSubraces` (homebrew race rows can carry `subraceOf`). A homebrew name that collides with a REAL sourcebook entry is NOT clobbered (the real one would be lost on strip).

**Seam (the structured-types engine, ≈ before `buildHbStudio`):** `HB_BAGS` = the 6 content types a source holds; `HB_BAG_LABEL` = display labels; `hbActiveByType(key)` = merged enabled entries; `hbApplyToData`/`hbStripData`/`hbStripClone` = the merge/strip engine; `HB_GEN_SPECS` = the field-spec registry for the 4 structured types (each: `fields[]`, `toObj` form→DATA-shape, `fromObj` DATA-shape→form, `summary`), driving ONE generic pane (`#hb-pane-gen`, `renderHbGen`/`hbSaveGenForm`/`hbDelGen`, state `_hbType`/`_hbGenEditKey`) reused across the Feats/Races/Backgrounds/Subclasses tabs — NOT four bespoke forms. **Saved copies serialize the LIVE DOM; runtime-built chrome must be stripped or it ships as a dead corpse (2.93.1).** `btn-savecopy` and `shareBlankSheet` serialize `document.documentElement.cloneNode(true)`, so any lazily-built, listener-wired element that exists at save time rides into the file as markup with ZERO listeners (listeners never serialize). An already-corpsed file runs its own old code, so it can't self-heal until updated: rescue by cutting the corpse div(s) out of the file tail (they sit after the last `</script>`; back up first), which preserves the baked characters/homebrew exactly. **Rescue-by-`cp` caveat (supersedes the bare "cp a good build over it" advice): a file that carries baked characters partitions its storage by `BASE_KEY = "dnd-sheet-file-" + hash(embedded-data payload)` (≈2998; savedAt/portrait/contentHash excluded from the hash). **Updates refresh SOURCE DATA additively, not just the app code (2.99.0). `mergeUpdatedSources` now routes through `additiveMergeSources(user, fresh)` (both ≈13525).** The old function had a size-heuristic branch (`_ver` tie && `_size(user) >= _size(shipped)` → keep user whole) that SILENTLY SKIPPED genuinely-new entries whenever the user had more TOTAL content than the shipped build (e.g. a personal file with extra adventures loaded) — so a build that added a few spells within an existing book never reached that user. `additiveMergeSources` folds the fresh build's content INTO the user's data: per collection (spells/races/items/monsters/maps), entries the user LACKS are added and an OFFICIAL entry whose **normalized content hash differs is refreshed** to the fresh version (errata / new-within-a-book). ## HP widget (Combat card)

The Combat card's HP block is the compact `.hpbox` widget, modeled on D&D Beyond: `Heal`/`Damage` buttons (`#hp-heal`/`#hp-damage`) around a number field (`#hp-delta`) on the left, big `Current / Max` digits centered with `Temp` right beside Max, and a `.hp-head` header above the box. Capped at `max-width:460px` so it reads as a small card, not a full-width bar (the combat card spans the whole top band in the landscape layout). `applyHpDelta(heal)` does the math: Damage absorbs into Temp HP first (5e RAW) then Current (floored at 0); Heal adds to Current capped at Max and NEVER touches Temp; the delta clears after applying so a stray double-click can't silently re-apply. **Current can never exceed Max** — `onChange` clamps `#hpcur` to `#hpmax`, and `recalcMaxHp()` re-clamps it whenever Max changes. **Temp (`#hptmp`) is uncapped** (floored at 0 via `min="0"`); it reads as a plain muted number but tap/hover reveals a bordered stepper box (CSS-only `:hover`/`:focus` reveal, no JS). Reason: the desktop side-by-side split (≈94px controls + ~206px readout) starves the readout in the narrow combat card, and `.hp-big` is pinned at `width:3.6ch` — too narrow for a 3-digit value at the 30px readout size, so 152/152/188 clipped against each other and the slash; no font/width tweak fits THREE 3-digit numbers in 206px, so the layout has to change. The mobile rule also widens `.hp-big` to `4.3ch` so 3 digits never clip. The clip is the INPUT's own fixed width vs its content (an `<input>` clips, `scrollWidth>clientWidth`), independent of surrounding space — widening the readout alone doesn't fix it, you must widen the field too. **Max HP is a baseline + modifier/override stack.** Tapping Max (`#hpmax`, now `readonly`) opens the `#hpmax-pop` popover (toggled in the delegated click handler; click-outside closes) with two stepper fields: `#hpmax-mod` (±, adjusts baseline) and `#hpmax-override` (replaces it, wins over the modifier). **Input-styling gotcha (bit me repeatedly):** global `input,select,textarea` (≈line 139) AND `body.dark input` (≈line 47) set border+background on every input, and a plain class rule does NOT out-specify the dark one. To show arrows only on hover/tap, keep them in layout with `opacity:0` at rest and `opacity:1` on `:hover`/`:focus` (don't toggle `display`, which reflows). Reserve a transparent 1px border at rest so revealing the box doesn't shift neighbors (with `box-sizing:content-box`). TWO MORE rules feed this gotcha (found fixing the Speed box, 2.92.0): the flat/sharp block (≈1134) forces `input{background:#fff !important}` and `input:focus{outline:none !important}`, and `body[data-theme="ucs"] input` (≈1746) adds `border:1px solid var(--line)` at (0,1,2) specificity, which BEATS `.stat input` (0,1,1) — so any "make this input look like a plain value" fix needs `border:none !important; background:transparent !important` on a ≥(0,2,2) selector PLUS the `body.dark` twin (the `.combat-top .stat input` rule ≈396 is the template). Non-text controls (buttons/tabs/checkboxes) get keyboard focus from one `:focus-visible` outline rule in the flat/sharp block (2.92.0) — keep it when touching that block.

## Mobile horizontal-scroll gotcha (iOS-only, not headless-reproducible)

- **"The mobile view scrolls left into empty space / graphical glitches" = the sticky `.pagetabs` overscroll (fixed 2.88.1).** `html.mobile .pagetabs` (CSS ≈1345) is `position:sticky; overflow-x:auto` with a `margin:0 -10px` edge-bleed so the swipeable tab strip reaches the screen edges. On a REAL iPhone that negative-margin overhang lets Safari rubber-band the whole document sideways into the blank -10px region (empty space + sticky-repaint glitches). **You cannot reproduce this headlessly** — Chromium AND authentic iPhone-13 WebKit (Playwright `p.devices["iPhone 13"]` + `p.webkit`) both report `maxScrollX:0` / `documentElement.scrollWidth == innerWidth` even under simulated tab-swipe/modal/every-page interaction; it's a real-device touch-momentum behavior. Fix = `html.mobile, html.mobile body{ overflow-x:clip; }` (≈1327). **Use `overflow-x:clip`, NOT `hidden`** — `clip` does not create a scroll container, so it leaves `position:sticky` (the pinned tab bar) and vertical document scrolling intact; `hidden` would break them. Verified on iPhone-13 WebKit: no h-scroll, tab bar still scrolls internally + stays pinned (`top:0` after a vertical scroll), page scrolls vertically. General lesson: for a "phantom sideways scroll on iPhone only" report, suspect a sticky/negative-margin/`overflow-x` element and reach for `overflow-x:clip` on the mobile document rather than chasing a headless repro.
