# D&D Character Sheet

Alex's from-scratch, single-file D&D 5e (2014 rules) character sheet app — a clean-room replacement for MPMB's PDF sheet, built because MPMB's automation is inseparable from its Adobe/look (reskin proven impossible). The whole app is one self-contained `index.html`: inline CSS + JS, no frameworks, no Adobe or proprietary software required to view it, with the full 5etools sourcebook baked into a `#source-data` `<script>` (~5MB of the ~13MB file) so GitHub Pages serves it self-contained and it works fully offline.

- **Local repo:** `~/Documents/dnd-character-sheet`
- **GitHub:** `BaesTheorem/dnd-character-sheet` (`main`, origin set, gh auth = BaesTheorem)
- **The app:** `index.html` (~13MB). That's it. Everything ships in this one file.
- **Deploy = push to `main`.** Alex runs the GitHub Pages build (`baestheorem.github.io/dnd-character-sheet`), not the local file or stale Drive/iCloud copies. When he says "I don't see my change," the answer is almost always "reload the Pages tab," not a code bug.

## Testing protocol (this matters — read it)

The `<script>`-extract-then-`node --check` syntax check is **UNRELIABLE** on this ~13MB file: a `</script>` literal inside a string truncates the regex extraction (false "Unexpected end of input"); brace-count deltas are noise from strings/regex. A duplicated `function compute(){` once would have shipped a fully-broken sheet and node-on-extracted-script missed it.

**Always verify edits by loading the page in Playwright** and checking `page.on("pageerror")` + `typeof compute === 'function'`. That catches the real breaks. When an Edit looks balanced but the page breaks, `git diff` to spot an accidental duplicated/dropped line (a common cause: an Edit `new_string` that re-includes the trailing context line).

- **Playwright = the PYTHON package** (`/opt/homebrew/bin/playwright`, `pip install --break-system-packages playwright && python3 -m playwright install chromium`), NOT Node. Click `#intro-skip` to dismiss the welcome overlay.
- **Do NOT use `--headless=old`** on this file — it renders the whole `<style>` block as visible body text (a headless artifact, not a real bug) and `--dump-dom` can DEADLOCK forever (a render once hung 57 min and froze the whole session). macOS has no `timeout` binary (use `gtimeout` or a `&`+poll watchdog). Prefer the **browser-render skill** for flash-free capture, or Playwright `evaluate()` + `full_page` screenshot. If a render hangs: kill the Chrome chain on `user-data-dir=/tmp/render-e` + `rm -rf` the lock dir.
- **Preview a theme** by copying index.html and swapping `const DEFAULT_THEME = "ucs"` → the target theme id, and `let darkMode = prefBool(DARK_KEY)` → `true` for dark.
- **Headless test seams** (things that don't render the way you'd expect): hand-pushed `asiChoices` get wiped by `compute()→syncAsiSlots()` (truncates to `asiCount()`, 0 without a class) — set `#classlevel='Fighter 4'` for a real slot; the ASI panel DOM only renders when its panel is open. Class-resource Limited rows (Arcane Recovery, Channel Divinity, Bardic Inspiration) come from `LIMITED_RESOURCES` via `fillLimitedFeatures(cls,lvl)` at char generation, NOT `refreshLimitedFeatures` — seed them to test. Write-in spell rows hold the name in an INPUT VALUE, not textContent (search `input.sp-name` value). A headless wizard sheet needs `spellMaxByInst[0]=9` + `spellEntriesOf(0)[L]` set to render spell rows.

## Keep app CODE copyright-clean (load-bearing constraint)

Alex may one day **sell or more widely distribute the sheet itself**, so the app code must stay free of copyrighted WotC material. The design rule: **the baked `#source-data` blob is the ONLY place copyrighted content is allowed to live.** Null out `#source-data` and what's left should be a copyright-clean app (point it at a 5etools source to reconstitute). The whole-file-with-data-baked-in is fine for Alex's own use *today*; the separation is what keeps a future strip-and-sell viable.

**What this means for every edit that adds content:**
- Never hardcode copyrightable WotC TEXT into app JS (spell/feature/item/invocation/maneuver/metamagic/fighting-style descriptions, stat-block prose). It belongs in `#source-data`, pulled in by a loader. This is already done — `OPTIONAL_FEATURES` and `FIGHTING_STYLES` text were de-baked into `#source-data` (via `etOptionalFeatures`) so app code is text-free. Keep it that way; don't reintroduce verbatim text into a registry.
- **Names + mechanics + formulas are NOT copyrightable** and are fine to keep hardcoded — that's why the hand-coded registries (`FEAT_SPELLS`, `FEAT_SKILLS`, `FEATURE_ATTACKS`, `LIMITED_RESOURCES`, `ELSEWHERE_ITEMS`) live in app JS and survive a rebake. Alex's OWN paraphrase prose (`SPELL_CHANGES`, `TCE_RULES`) is also fine to keep — it's his words.
- Audit reference: nulling `#source-data` takes the file ~13.3MB → ~2.85MB with a graceful "load a sourcebook" prompt; reload works via a local 5etools server OR a CORS mirror (e.g. the jsDelivr 5etools-2014 mirror). If you add a new content type, route its TEXT through `#source-data` + a loader, not into app code.

## Architecture / where things live

- **Storage = IndexedDB** (`dnd-sheet` db): char data + portraits + thumbnails, fronted by a synchronous in-memory cache `_cs` (moved off localStorage to escape the ~10MB cap). `SOURCES_KEY` + settings stay in localStorage. Opening a sheet that carries baked characters partitions into `dnd-sheet-file-<hash>` localStorage so it shows the FILE's chars, not yours.
- **Runtime data = the baked `#source-data`** (`DATA_VERSION` const, now 31+). `source-data.json` is a gitignored, STALE local artifact and `build-data.py` is the offline CLI baker (reads local 5etools → `source-data.json`, never writes the committed index.html). Do NOT run a full `build-data.py` rebuild to ship data — it's behind on hand-patched fields and regresses. New data gets injected SURGICALLY into `#source-data` via Python string-insert (the established pattern for itemSpells, attackSpells, draconic ancestry, etc.).
- **Three data representations that DIVERGED, not duplication to collapse:** (1) `build-data.py` = global superset baker (extracts across ALL 5etools files), (2) the in-browser JS loader `etBook`/`mergeBook`/`bakeSourceData()` = the LIVE per-loaded-book generator, (3) the baked `#source-data` that ships. `build-data.py` is NOT redundant/deletable — keep it. - **Spell sheets are driven by the `CASTERS` map (≈line 5314), keyed by class OR `"Class (Subclass)"`** (e.g. `"Monk (Way of Shadow)"`, `"Fighter (Eldritch Knight)"`). An entry can be a slot/known caster (`ability`, `prepares`, `fullList`, `ritual`) or a **`fixed`** caster — `{fixed:{0:["Minor Illusion"],2:["Darkness",…]}, noSlots:true}` — meaning "exactly these always-known spells, no slots, no blank rows" (`renderSpellTable` ≈line 5814 renders the fixed list straight from `spellData(name)`). ### The DATA_VERSION gotcha (causes "Sourcebooks out of date" forever)

When you bump the `DATA_VERSION` const, you **MUST also re-stamp the baked `#source-data` `_meta.dataVersion`** to match (there's exactly ONE `"dataVersion":N` in the baked blob, in `_meta` before `"pendingAug"`). A const-only bump makes the baked data SELF-STALE; a clobbered stored copy ties-and-wins and the flag shows forever. Because the Edit tool's file-state tracking fights this 13MB file (and SOH `\x01` separators in some sigs can't be matched by Edit at all), use a **verified Python byte-level replace** for these edits, not the Edit tool.

## Themes

There are effectively **two** themes. The brand "D&D Beyond" is FULLY SCRUBBED from the app (to avoid treading on the trademark): the old standalone "Universal" theme and the former "D&D Beyond" theme are one theme, displayed AND internally identified as **"Universal Character Sheet"**. There is no `dndbeyond`/`ddb` anywhere except one save-compat migration literal. Don't treat Universal and D&D Beyond as separate options, and don't reintroduce the brand name (UI, comments, or identifiers).

- **Conditions & Exhaustion engine:** Defenses is a subsection inside the Combat card (`.combat-sub`), with a **Conditions** subsection beside it. `CONDITIONS` (app-JS registry: key, name, *paraphrased* rules text = copyright-clean, and an `eff` object) + `EXHAUSTION_STAGES` drive everything. `buildConditionsPanel()` (called in `init()` BEFORE `applyAll` so the `data-save` inputs exist to restore) builds `#cond-panel`: one `#cond-<key>` toggle + expandable rules per condition, plus a 6-pip `#exhaustion` tracker. **`#cond-panel` lives in a popup `#cond-modal` (`.modal`/`.open`)**, opened by the "Manage conditions" button; the conditions-sub only shows the active chips + button. `condEffects()` aggregates active conditions + exhaustion into `{disadv:Set, adv:Set, speedZero, speedHalf, hpHalf, incap}` where adv/disadv tags are `attack`/`check`/`save`/`save:str`/`save:dex`. Auto-applied in `compute()`: **speed** (the `#speed` write applies `conditionSpeed()` → 0 or half), **HP max** (`recalcMaxHp()` halves on exhaustion ≥4), and **adv/disadv markers** via `renderConditionMarks()` (MUST run last in compute, after roll values are written) — `setAdvMark(box,…)` pins a green-A/red-D d20 (`advIconSvg()`, inline SVG) as an absolute corner badge (`.advmark` + `.advmark-host`) on the upper-right of each value's box — the skill/save total boxes (`#sktot-*`/`#savetot-*`), the Initiative `.stat`, and each filled attack row's Bonus `<td>`. `compute()` rewrites the total's textContent so the badge is re-appended each pass (hence renderConditionMarks runs last). `advFor()` cancels when both adv & disadv apply. `renderConditions()` paints the active-chip row + panel state. **Feature-granted adv/disadv:** `featureAdvEntries()` detects, from race / class+level / Features text / equipped armor, advantages & disadvantages on specific rolls (e.g. Barbarian Rage, Gnome Cunning, armor Stealth penalty). `gatherAdvSources()` merges condition + feature sources into a `target → [{kind,note}]` map (targets now include `skill:<key>`); `resolveAdv(map, keys)` cancels adv-vs-disadv and joins the situational notes for the tooltip. **To wire a new feature/feat/spell, add one entry to `featureAdvEntries()`** — `{kind:'adv'|'disadv', targets:['skill:stealth'|'save:wis'|'check'|'attack'|…], note:'when it applies'}` — and it flows through automatically. Most feature advantages are conditional, so the note states the condition (the marker is a reminder). Rules sourced from 5etools `conditionsdiseases.json` (PHB), paraphrased.
- **`scanDefenses(text)` is a SEPARATE prose-scanner** (≈line 3299, distinct from `featureAdvEntries()`): it regex-pulls resistances/immunities and granted (dis)advantages out of feature text into short lines, spliced into the editable `#defnotes` box **once at character creation/Edit** (line ~10535) and then persisted. It does NOT rebuild each `compute()`, so a stale/bad line stays in a saved character until the user deletes it by hand. The recurring trap: feature prose where "you have advantage" is a *condition*, not a *grant* (Sneak Attack: "...**if** you have advantage on the attack roll"; Assassinate; "...you don't have disadvantage...") — the scanner used to misread these and emit a garbled "Adv. on the attacks". Guard added: a `condAdv` test skips the four adv/disadv branches when the clause is governed by if/when/unless/whether/provided/even-if/so-long-as + "you have/gain (dis)advantage". `_tidyAdvMid` also now strips a lone article (`/^(?:an?|the)\b\s*/`) so a bare "the attack rolls" renders as "attacks", not "the attacks". When adding a new adv-granting feature, prefer one `featureAdvEntries()` entry (drives the live d20 markers) over relying on the prose scanner. **The race-trait scrape (≈line 8301) filters out the Warforged `Integrated Protection` trait** before scanning: its only (dis)advantage is the Heavy Plating mode's "disadvantage on Dexterity (Stealth) checks", which is mode-CONDITIONAL (not always-on) and already applied live via `featureAdvEntries()` when Heavy Plating is selected — scraping it into `#defnotes` at race pick was wrong and unconditional. General lesson: if a trait states a (dis)advantage that's gated behind a *mode/option choice within that trait* (not an if/when clause `condAdv` catches), exclude that trait from the scrape and handle the conditional live instead. Because the scrape only ADDS (never removes), a character made before such a fix keeps the stale line until deleted by hand.
- **Shield detection is name-based (`shieldBonus(name)`, ≈line 8852).** Any equipped item whose name matches `\bshield\b` grants +2 AC (+N for a magic "+N"), and the same function gates the inventory Equip checkbox (line ~9396 `eq`) and `hasEquippedShield()`. Real shields can't be required to END in "shield" (e.g. "Shield of Missile Attraction", "Shield of the Tortoise"), so the function excludes by competing item-type noun instead: `scroll` ("Scroll of Shield"), plus accessory/wondrous slot nouns (amulet/ring/brooch/cloak/wand/…) so "Shield Guardian Amulet" and "Ring of Shield" don't equip as shields. This was verified against 5etools item data: across the whole catalog the ONLY non-shield item matching `\bshield\b` is "Shield Guardian Amulet", and no type-`S` shield carries any excluded noun. When a new "shield"-named non-shield surfaces, add its slot noun to that exclusion list rather than special-casing the item.
- **Attunement recognition is global, not just loaded books (`attuneSet()`, ≈line 8791).** The Equip checkbox (`refreshEquipToggles`, line ~9396) AND the Attunement picker filter (`refreshEquippedPickers`, ~8820) both route through `attuneSet()` — fix attunement eligibility in that one function. So `attuneSet()` seeds from `ATTUNE_ALL_NAMES` — a hardcoded app-JS `const Set` of every `reqAttune` item name (lowercased) across the whole 5etools catalog (~685 names, ~15KB). It's an app-JS const (NOT in `DATA`/`#source-data`) on purpose: a "Reload all sources" rebuilds `DATA` from loaded books and would drop a global list stored there, and names + the attunement fact are non-copyrightable mechanics (same rationale as the other hand-coded registries). This means a free-typed attunement item from an unloadable book still offers Equip + attune. No AC/spell-bonus side effects: loaded items are already in `DATA.attuneItems`, and global-only names aren't in any AC/spell-bonus map. Regenerate `ATTUNE_ALL_NAMES`: 5etools `items*.json` names where `reqAttune` is set, lowercased + sorted.
- **AC calc supports many alternate formulas, ALL hardcoded by class/race NAME** (the AC block, ≈line 6586, inside the `#armorsel`-driven compute path). Fighter's 2/3/4 tiers stay class+level driven (only Fighter has them). For a brand-new Extra-Attack source, add it to BOTH if it has a fixed subclass name (class+level for manual sheets), else just lean on the feature-name scan. **Extra Attack is excluded from the Action Economy summary** (`renderActionEconomy()` ≈line 10381 skips any `featureCards()` title matching `/^extra attack\b/i`) — it's already represented by the Attacks/Action box, so listing it as a separate Action was redundant. **Action bucketing uses a strong-vs-weak split (≈line 10413) to avoid double-listing:** a STRONG signal (`as an action` / `as a magic action` / `use|spend your/an action`) always buckets a feature under Action; a WEAK/contextual signal (`take the <X> action`, `action on your turn`) counts toward Action ONLY when the feature is NOT already a bonus/reaction — because in a bonus/reaction feature that phrase is the trigger or effect ("after you take the Attack action … as a bonus action" — Martial Arts/Flurry of Blows; "take the Dodge action as a bonus action" — Patient Defense; Rogue Cunning Action), not a separate Action cost. `isBonus`/`isReaction` come from the raw text; `isAction = strongAction || (weakAction && !isBonus && !isReaction)`. A feature with a real dual mode ("as an action … or as a bonus action …") still lists in both via the strong signal. ## Distribution model

Primary distribution is the **offline HTML file** (web/Pages is the iPhone-only exception), so there's no auto-update. The in-app "update available" banner polls `version.json` (Pages URL + raw.githubusercontent fallback, both CORS-open); `updateApp()` re-bakes the user's characters into a fresh download. `updateApp()` first re-checks `fetchLatestVersion()` and reports "You're already up to date" if nothing is newer (no needless re-download); during a real update it shows a spinner on both Update buttons (`.btn-busy`) and a download progress bar — `updProg()`/`updProgDone()` drive BOTH the Settings widget (`#update-progress*`) and the banner widget (`#ub-progress*`) via `UPD_PROG_WIDGETS`. A CRITICAL channel exists: a one-line root `update-note.txt` → the pre-commit hook folds it into `version.json` as `{critical:true, note}` → the banner bypasses the dismissed flag and resurfaces every load until they update (sticky — rides every release until you DELETE the file). KEY LIMIT: older clients ignore the extra fields, so a critical flag only reaches users already on a build that understands it; the fix-introducing update needs out-of-band notice too.

## HP widget (Combat card)

The Combat card's HP block is the compact `.hpbox` widget, modeled on D&D Beyond: `Heal`/`Damage` buttons (`#hp-heal`/`#hp-damage`) around a number field (`#hp-delta`) on the left, big `Current / Max` digits centered with `Temp` right beside Max, and a `.hp-head` header above the box. Capped at `max-width:460px` so it reads as a small card, not a full-width bar (the combat card spans the whole top band in the landscape layout). `applyHpDelta(heal)` does the math: Damage absorbs into Temp HP first (5e RAW) then Current (floored at 0); Heal adds to Current capped at Max and NEVER touches Temp; the delta clears after applying so a stray double-click can't silently re-apply. **Current can never exceed Max** — `onChange` clamps `#hpcur` to `#hpmax`, and `recalcMaxHp()` re-clamps it whenever Max changes. **Temp (`#hptmp`) is uncapped** (floored at 0 via `min="0"`); it reads as a plain muted number but tap/hover reveals a bordered stepper box (CSS-only `:hover`/`:focus` reveal, no JS). The `.deathsaves` row lives INSIDE `.hp-readout` now: `updateDeathSaves()` hides `.hp-vals` and shows the death saves in its place at ≤0 HP (Heal/Damage column stays), and restores the numbers above 0.

**Max HP is a baseline + modifier/override stack.** Tapping Max (`#hpmax`, now `readonly`) opens the `#hpmax-pop` popover (toggled in the delegated click handler; click-outside closes) with two stepper fields: `#hpmax-mod` (±, adjusts baseline) and `#hpmax-override` (replaces it, wins over the modifier). The **baseline** lives in a hidden `#hpmax-base` — `compute()` writes it from the per-level HP rolls (it no longer writes `#hpmax` directly). `recalcMaxHp()` computes effective = `override ?? base+mod`, writes it into `#hpmax` (so every consumer still reads the effective max there), tints `#hpmax` green (`.hp-mod-up`)/red (`.hp-mod-down`) when it differs from baseline, and shows `(base)` in the `#hpmax-base-disp` span. Legacy/manual sheets with a value in `#hpmax` but no recorded base adopt it as baseline on first recalc; a pre-dialog `overrides.hpmax` pin migrates into the Override field; `hpmax` was removed from `overrideIds()`. `makeSimulacrumData` halves `hpmax-base` and clears mod/override too. The **Long Rest** dialog has a "Reset Max HP changes to baseline" checkbox (`#rest-resetmaxhp`, default on via `restState.resetMaxHp`) — `takeLongRest` clears mod/override and recalcs BEFORE restoring to full, so a reset heals to baseline not the buffed max; toggling it re-renders so the "Restored to full" target updates live. **The ids `#hpcur`/`#hpmax`/`#hptmp` are unchanged** (effective values) — that's what keeps `save()`, `compute()`, `updateDeathSaves()` (death-save row at ≤0), rests (`restHp`), and the Classic overlay sync working; preserve them in any HP rework. New persisted fields are plain `[data-save]` inputs, so they ride `save()`/`applyFields` automatically.

**Input-styling gotcha (bit me repeatedly):** global `input,select,textarea` (≈line 139) AND `body.dark input` (≈line 47) set border+background on every input, and a plain class rule does NOT out-specify the dark one. To make a borderless/box-free number field (the big HP digits) you need `border:none !important; background:transparent !important` on the class PLUS a `body.dark .hp-big{…!important}` override (and for Temp's reveal, a `body.dark .hp-tempin` border reset too). Separately, `input[type=number]{appearance:textfield}` (≈line 145) hides spinners on ALL number inputs — to bring spinner arrows back on one field (`#hp-delta`, `.hp-tempin`) set `appearance:auto` (+ `-moz-appearance:textfield`) and the `::-webkit-*-spin-button{-webkit-appearance:inner-spin-button;appearance:auto}` pseudos. To show arrows only on hover/tap, keep them in layout with `opacity:0` at rest and `opacity:1` on `:hover`/`:focus` (don't toggle `display`, which reflows). Reserve a transparent 1px border at rest so revealing the box doesn't shift neighbors (with `box-sizing:content-box`).
