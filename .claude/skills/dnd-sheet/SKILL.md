# D&D Character Sheet

Alex's from-scratch, single-file D&D 5e (2014 rules) character sheet app — a clean-room replacement for MPMB's PDF sheet, built because MPMB's automation is inseparable from its Adobe/look (reskin proven impossible). The whole app is one self-contained `index.html`: inline CSS + JS, no frameworks, no Adobe or proprietary software required to view it, with the full 5etools sourcebook baked into a `#source-data` `<script>` (~5MB of the ~13MB file) so GitHub Pages serves it self-contained and it works fully offline.

- **Local repo:** `~/Documents/dnd-character-sheet`
- **GitHub:** `BaesTheorem/dnd-character-sheet` (`main`, origin set, gh auth = BaesTheorem)
- **The app:** `index.html` (~13MB). That's it. Everything ships in this one file.
- **Deploy = push to `main`.** Alex runs the GitHub Pages build (`baestheorem.github.io/dnd-character-sheet`), not the local file or stale Drive/iCloud copies. When he says "I don't see my change," the answer is almost always "reload the Pages tab," not a code bug.

## First moves every session

1. **`grep` on `index.html` WILL hit the baked data blob — expect it before your first grep, don't get surprised and redirect.** You read this file by grepping constantly, and ~5MB of WotC JSON lives in the `#source-data` `<script>` as ONE physical line (plus base64 at the `PAGES` line). So `grep -n "<term>"` for anything that also appears in the data (`edition`, `bakedBooks`, `name`, `text`, spell/feature names, common words) prints that whole multi-MB line and overflows the tool output (bare `grep -n "edition"` dumped 19MB once). Two habits: (a) **anchor on code-only tokens** that can't be in JSON — `grep -n "function isBook2024"`, `grep -n "const RULESET_2024"`, `grep -n 'id="loaded-books"'`; (b) when a term might be in the data, **don't print the matched line raw** — `grep -n "term" index.html | awk -F: '{print $1}'` (line numbers only) or `| cut -c1-160`, then `Read` that line range.
2. **Read `VERSION`** (current SemVer) and the top of the in-app changelog before bumping anything. Alex commits in PARALLEL during sessions — a stale assumption about the current version will regress it (I once clobbered 2.32.0→2.31.1). Never assume the last value you set is current; re-read first.
3. **For ANY D&D rules value, read the source data — never use memory.** This is absolute here. My recall of stat blocks, spell dice, level progressions, feature text, DCs, HP formulas has been wrong repeatedly and silently corrupted the sheet (shipped Primal Companion from memory, got passive Perception / HP formula / attack dice / grapple DC all wrong). Pull from `~/My Drive/5etools/data` (override via `FIVETOOLS_DATA`; same path `build-data.py` uses). A server may run at `http://localhost:5050` but is often down — the raw JSON on disk is always there. Key files: `class/class-<class>.json`, `optionalfeatures.json` (FS:*/EI/MV:B/MM by featureType), `bestiary/bestiary-<src>.json`, `spells/`, `races.json`, `feats.json`, `items.json`, `magicvariants.json`. Strip `{@tag ...}` markup when reading. Verify finished work with a programmatic diff against source when feasible.
4. At the end of every change set, follow **"After every change set" below** — auto-commit + push, then update THIS skill with anything new you learned.

## Two version numbers (do not conflate)

- **`APP_VERSION` = `vN`** — a build id the `.githooks/pre-commit` hook auto-bumps EVERY commit. Drives update detection + `sw.js` cache-bust. Don't hand-edit.
- **`APP_SEMVER`** — read from the `VERSION` file, HAND-CURATED. The app shows/names downloads by SemVer (`appLabel()`), so if you don't bump `VERSION`, the visible version looks frozen even as code ships. **Bump `VERSION` on EVERY commit that changes shipped `index.html` code — MINOR for features, PATCH for fixes AND for internal-only changes (refactors, renames, new migration paths).** "No visible change" is NOT a reason to hold the SemVer flat — Alex corrected this explicitly: a real code change that ships still warrants at least a PATCH, so the version history reflects that the code moved. The only commits that skip the bump are ones that don't touch shipped `index.html` (tooling, `build-data.py`), which also use `--no-verify`. Report the SemVer to Alex (e.g. "2.39.2"), never the `vN` build number — SemVer is what he thinks in. The hook prints both after commit. To add a note, drop a top `{v:"Unreleased", items:[...]}` changelog entry; the hook stamps it with the version on commit.
- The repo sets `core.hooksPath .githooks`; fresh clones must set it or the stamp won't run.
- Use `git commit --no-verify` for any commit that does NOT change shipped `index.html` (e.g. `build-data.py`, coverage tooling) so the hook doesn't bump `APP_VERSION` and trigger a no-op 13MB "update available" for offline players.

## Testing protocol (this matters — read it)

The `<script>`-extract-then-`node --check` syntax check is **UNRELIABLE** on this ~13MB file: a `</script>` literal inside a string truncates the regex extraction (false "Unexpected end of input"); brace-count deltas are noise from strings/regex. A duplicated `function compute(){` once would have shipped a fully-broken sheet and node-on-extracted-script missed it.

**Always verify edits by loading the page in Playwright** and checking `page.on("pageerror")` + `typeof compute === 'function'`. That catches the real breaks. When an Edit looks balanced but the page breaks, `git diff` to spot an accidental duplicated/dropped line (a common cause: an Edit `new_string` that re-includes the trailing context line).

- **`grep` hits the baked data blob** — see First moves #1 (anchor on code-only tokens, or line-numbers-only / `cut -c1-160`); it's the very first thing to internalize because reading this file means grepping it.
- **Playwright = the PYTHON package** (`/opt/homebrew/bin/playwright`, `pip install --break-system-packages playwright && python3 -m playwright install chromium`), NOT Node. Click `#intro-skip` to dismiss the welcome overlay.
- **Do NOT use `--headless=old`** on this file — it renders the whole `<style>` block as visible body text (a headless artifact, not a real bug) and `--dump-dom` can DEADLOCK forever (a render once hung 57 min and froze the whole session). macOS has no `timeout` binary (use `gtimeout` or a `&`+poll watchdog). Prefer the **browser-render skill** for flash-free capture, or Playwright `evaluate()` + `full_page` screenshot. If a render hangs: kill the Chrome chain on `user-data-dir=/tmp/render-e` + `rm -rf` the lock dir.
- **Preview a theme** by copying index.html and swapping `const DEFAULT_THEME = "ucs"` → the target theme id, and `let darkMode = prefBool(DARK_KEY)` → `true` for dark.
- **Headless test seams** (things that don't render the way you'd expect): hand-pushed `asiChoices` get wiped by `compute()→syncAsiSlots()` (truncates to `asiCount()`, 0 without a class) — set `#classlevel='Fighter 4'` for a real slot; the ASI panel DOM only renders when its panel is open. Class-resource Limited rows (Arcane Recovery, Channel Divinity, Bardic Inspiration) come from `LIMITED_RESOURCES` via `fillLimitedFeatures(cls,lvl)` at char generation, NOT `refreshLimitedFeatures` — seed them to test. Write-in spell rows hold the name in an INPUT VALUE, not textContent (search `input.sp-name` value). A headless wizard sheet needs `spellMaxByInst[0]=9` + `spellEntriesOf(0)[L]` set to render spell rows.

## Keep app CODE copyright-clean (load-bearing constraint)

Alex may one day **sell or more widely distribute the sheet itself**, so the app code must stay free of copyrighted WotC material. The design rule: **the baked `#source-data` blob is the ONLY place copyrighted content is allowed to live.** Null out `#source-data` and what's left should be a copyright-clean app (point it at a 5etools source to reconstitute). The whole-file-with-data-baked-in is fine for Alex's own use *today*; the separation is what keeps a future strip-and-sell viable.

**What this means for every edit that adds content:**
- Never hardcode copyrightable WotC TEXT into app JS (spell/feature/item/invocation/maneuver/metamagic/fighting-style descriptions, stat-block prose). It belongs in `#source-data`, pulled in by a loader. This is already done — `OPTIONAL_FEATURES` and `FIGHTING_STYLES` text were de-baked into `#source-data` (via `etOptionalFeatures`) so app code is text-free. Keep it that way; don't reintroduce verbatim text into a registry.
- **Names + mechanics + formulas are NOT copyrightable** and are fine to keep hardcoded — that's why the hand-coded registries (`FEAT_SPELLS`, `FEAT_SKILLS`, `FEATURE_ATTACKS`, `LIMITED_RESOURCES`, `ELSEWHERE_ITEMS`) live in app JS and survive a rebake. Alex's OWN paraphrase prose (`SPELL_CHANGES`, `TCE_RULES`) is also fine to keep — it's his words.
- Audit reference: nulling `#source-data` takes the file ~13.3MB → ~2.85MB with a graceful "load a sourcebook" prompt; reload works via a local 5etools server OR a CORS mirror (e.g. the jsDelivr 5etools-2014 mirror). If you add a new content type, route its TEXT through `#source-data` + a loader, not into app code.

## Architecture / where things live

- **Storage = IndexedDB** (`dnd-sheet` db): char data + portraits + thumbnails, fronted by a synchronous in-memory cache `_cs` (moved off localStorage to escape the ~10MB cap). `SOURCES_KEY` + settings stay in localStorage. Opening a sheet that carries baked characters partitions into `dnd-sheet-file-<hash>` localStorage so it shows the FILE's chars, not yours.
- **Runtime data = the baked `#source-data`** (`DATA_VERSION` const, now 31+). `source-data.json` is a gitignored, STALE local artifact and `build-data.py` is the offline CLI baker (reads local 5etools → `source-data.json`, never writes the committed index.html). Do NOT run a full `build-data.py` rebuild to ship data — it's behind on hand-patched fields and regresses. New data gets injected SURGICALLY into `#source-data` via Python string-insert (the established pattern for itemSpells, attackSpells, draconic ancestry, etc.).
- **Three data representations that DIVERGED, not duplication to collapse:** (1) `build-data.py` = global superset baker (extracts across ALL 5etools files), (2) the in-browser JS loader `etBook`/`mergeBook`/`bakeSourceData()` = the LIVE per-loaded-book generator, (3) the baked `#source-data` that ships. `build-data.py` is NOT redundant/deletable — keep it. Watch the JS loader for silent drift: it can lag the baker and drop hand-patched fields on a "Reload all sources" — keep the two at parity.
- **Hand-coded registries survive a rebake** (names + mechanics, non-copyrightable, or Alex's own prose): `FEAT_SPELLS`, `FEAT_SKILLS`, `FEATURE_ATTACKS`, `LIMITED_RESOURCES`, `SPELL_CHANGES`, `ELSEWHERE_ITEMS`, `TCE_RULES`. Base-class feature choices (Fighting Styles, Infusions, invocations/metamagic/maneuvers) are hand-coded in app JS too (names/mechanics only — their TEXT lives in `#source-data`, per "Keep app code copyright-clean" above).

### The DATA_VERSION gotcha (causes "Sourcebooks out of date" forever)

When you bump the `DATA_VERSION` const, you **MUST also re-stamp the baked `#source-data` `_meta.dataVersion`** to match (there's exactly ONE `"dataVersion":N` in the baked blob, in `_meta` before `"pendingAug"`). A const-only bump makes the baked data SELF-STALE; a clobbered stored copy ties-and-wins and the flag shows forever. Because the Edit tool's file-state tracking fights this 13MB file (and SOH `\x01` separators in some sigs can't be matched by Edit at all), use a **verified Python byte-level replace** for these edits, not the Edit tool.

## Homebrew Builder (the three-step workflow for fully fleshing out homebrew)

When Alex wants to create homebrew material (a spell, item, and eventually a feat/race/subclass/class/background), drive it through these THREE steps in order. The point is that the finished piece ends up as a portable JSON file that, when imported, gets **first-class mechanical support** on the sheet (auto-applied AC/attack/DC/attunement/etc.), not just stored as inert text.

**Step 1 — Iterate on the material itself, together.** Design it WITH Alex before touching code. Settle the name, the rules text, and (critically) the *mechanics*: what numbers/effects it grants and under what conditions. Ground every rules value in real D&D data (`~/My Drive/5etools/data`) per the absolute "never from memory" rule at the top of this skill. Decide the balance/tier. The deliverable of this step is an agreed spec: exactly what the thing does, in mechanical terms.

**Step 2 — Modify the sheet code to support its mechanics (only if needed).** Check whether the existing homebrew schema + engines already cover the mechanics:
  - A plain **spell** (level/school/components/text/higher) or a **magic item** whose effects are AC bonus / spell-attack bonus / spell-save-DC bonus / attunement / weapon math (Ancestral Weapon) — **no code change needed.** The current homebrew item/spell shapes + the existing overlay functions (`hbActiveItems`/`hbActiveSpells`/`hbEnabledItem`/`acItemMap`/`spellBonusItemMap`/`attuneSet`/`allItemText`, and `awDerive`/`hbAwMagicWeapon` for AW) already auto-apply these. Skip to step 3.
  - A mechanic **beyond** that (a novel rider, a new resource, a feat that grants a skill/attack, a race trait with a special AC formula, etc.) — extend the sheet using the **proven injection recipe** (the same one items + AW follow): store the new field on the per-source object, add/extend a normalizer, and inject an `hbActive<Type>()` (or new field handler) **at that mechanic's resolver read points** — NEVER merge homebrew into `DATA`/`mergeBook` (homebrew is a carried key, not a merged book). For copyright cleanliness, names+mechanics+formulas stay in app JS; verbatim copyrighted TEXT rides `#source-data` (see "Keep app CODE copyright-clean"). Bump SemVer for the code change.

**Step 3 — Encode it as a homebrew JSON file for first-class import.** Author the finished material as a homebrew JSON envelope and import it via the Homebrew Studio's **"Import JSON…"** button (it merges into the *currently selected* source). Because import routes each entry through the same normalizer + storage as the in-app forms, the imported content gets identical first-class treatment. The envelope (shipped 2.67.0):
```json
{
  "_meta": { "homebrew": true, "name": "Source name (optional)" },
  "spells": [ { "name":"…", "level":2, "school":"Evocation", "components":"VS",
               "time":"1 action", "range":"60 feet", "duration":"Instantaneous",
               "material":"", "conc":true, "ritual":false, "text":"…", "higher":"…" } ],
  "items":  [ { "name":"…", "type":"Wondrous Item", "rarity":"Rare", "attune":true,
               "acBonus":0, "spellAtk":0, "spellDc":0, "text":"…",
               "aw":{ … } } ]
}
```
Each content type accepts an **array OR an object map** (`{lowercase-name: obj}`); merge is additive, by lowercased name, last-wins. `components` tolerates 5etools-style `{v,s,m}` (normalized to a `"VSM"` string). An `items[].aw` blob (Ancestral Weapon build) is preserved and round-trips; if present, an **export** also bundles the AW upgrade catalog + text so the file is self-contained. A full **sourcebook**-schema file (`races`/`classes`/`spells` as top-level arrays) is rejected here with a pointer to Settings → Import files… — don't conflate the two import paths.

**Code seam (all ≈ the `importAwContent` neighborhood, before `buildHbStudio`):** `HB_IMPORT_TYPES` is the **single registry** of homebrew content types — `[{key, label, norm}]`, currently `spells` + `items`. `normHbSpell`/`normHbItem` coerce a loose object into the stored shape. `hbImportIntoSource(idx, d)` merges a parsed file into `homebrewSources[idx]` (returns `{counts, total, name}` or `{err}`); `hbExportSource(idx)` writes the selected source out (`download`). `hbAwBundleInto(d)` folds AW upgrade defs+text and is shared by `importAwContent` + the homebrew importer (DRY — don't reintroduce a second copy). UI: `#hb-src-import`/`#hb-src-export` buttons + a hidden `#hb-import-file` in the Studio's `.hb-src-row`, wired in `buildHbStudio`; success/skip is summarized generically from `HB_IMPORT_TYPES` labels.

**Two injection strategies — pick by how the builder reads the type:**
- **Lookup-overlay (spells, items):** the read points go through centralized lookup fns, so overlay enabled homebrew there (`hbActiveSpells`/`hbActiveItems`/`hbEnabledItem`/`spellData` precedence). Homebrew is NEVER put into `DATA`.
- **Merge-into-DATA (feats, races/subraces, backgrounds, subclasses — SHIPPED 2.68.0):** the builder reads these from the live `DATA` arrays in DOZENS of scattered places (race picker + `applyRace`, feat pickers + `applyAsiBonuses`, background picker + `applyBackground`, subclass picker + feature-by-level application), so per-read overlay is impractical. ## Distribution model

**The service worker (`sw.js`) is self-healing as of 2.80.0 — a stale/broken cache can NEVER strand a hosted/Pages user, and users never run code or reload by hand. Do not regress this to cache-first.** The failure it fixes: the old stale-while-revalidate SW served the cached document FIRST every load, so a broken cached build (its `DATA` came back null) kept being served and its own broken updater JS couldn't rescue it → user stuck until a manual SW clear. Now: the **main DOCUMENT is network-first** (`networkFirstDoc`, a `fetch(req,{cache:"no-cache"})` revalidating request → cheap 304 when unchanged, full body only on a real deploy; falls back to cache ONLY when the network is unreachable, so offline still works fully), everything else stays stale-while-revalidate for speed. The `#source-data`-carrying document is the only thing that must be fresh, and the SW (not the possibly-broken app JS) owns that. Registration (`index.html` ≈11873) uses `updateViaCache:"none"` (browser always revalidates `sw.js` itself, so a new worker is always noticed), `reg.update()` on load / return-to-tab / hourly, and a `controllerchange` handler that reloads an ALREADY-controlled tab exactly ONCE when a new worker activates (`wasControlled` guard: a first-ever visit has no controller, so it never reloads → no first-visit reload, no loop). Verified with a served fixture (network-first serves a fresh deploy online, offline falls back to cache, a new SW self-heals with exactly one reload, IndexedDB untouched). The `.githooks/pre-commit` hook stamps `const CACHE = "dnd-sheet-v<N>"` in `sw.js` (keep that exact line shape) so each deploy drops the old cache. Primary distribution is still the **offline HTML file** (web/Pages is the iPhone-only exception). The in-app "update available" banner polls `version.json` (Pages URL + raw.githubusercontent fallback, both CORS-open); `updateApp()` re-bakes the user's characters into a fresh download. `updateApp()` first re-checks `fetchLatestVersion()` and reports "You're already up to date" if nothing is newer (no needless re-download); during a real update it shows a spinner on both Update buttons (`.btn-busy`) and a download progress bar — `updProg(pct,label)`/`updProgDone()` drive BOTH the Settings widget (`#update-progress*`) and the banner widget (`#ub-progress*`) via `UPD_PROG_WIDGETS` (4-tuples `[wrap,fill,label,pct]`). **Real progress on BOTH paths (2.70.0):** the local-file download streams via `fetchLatestApp(onProgress)` (Content-Length → %); the HOSTED/Pages path no longer does a blind `location.reload()` — it clears SW+caches, then streams the new `index.html` (real download %, warming the HTTP cache) and reloads. `updProg` shows the % as a number in a dedicated `.upd-prog-pct` element AND the bar fill (pct null = indeterminate sliding bar + blank %). A CRITICAL channel exists: a one-line root `update-note.txt` → the pre-commit hook folds it into `version.json` as `{critical:true, note}` → the banner bypasses the dismissed flag and resurfaces every load until they update (sticky — rides every release until you DELETE the file). KEY LIMIT: older clients ignore the extra fields, so a critical flag only reaches users already on a build that understands it; the fix-introducing update needs out-of-band notice too.

## HP widget (Combat card)

The Combat card's HP block is the compact `.hpbox` widget, modeled on D&D Beyond: `Heal`/`Damage` buttons (`#hp-heal`/`#hp-damage`) around a number field (`#hp-delta`) on the left, big `Current / Max` digits centered with `Temp` right beside Max, and a `.hp-head` header above the box. Capped at `max-width:460px` so it reads as a small card, not a full-width bar (the combat card spans the whole top band in the landscape layout). `applyHpDelta(heal)` does the math: Damage absorbs into Temp HP first (5e RAW) then Current (floored at 0); Heal adds to Current capped at Max and NEVER touches Temp; the delta clears after applying so a stray double-click can't silently re-apply. **Current can never exceed Max** — `onChange` clamps `#hpcur` to `#hpmax`, and `recalcMaxHp()` re-clamps it whenever Max changes. **Temp (`#hptmp`) is uncapped** (floored at 0 via `min="0"`); it reads as a plain muted number but tap/hover reveals a bordered stepper box (CSS-only `:hover`/`:focus` reveal, no JS). The `.deathsaves` row lives INSIDE `.hp-readout` now: `updateDeathSaves()` hides `.hp-vals` and shows the death saves in its place at ≤0 HP (Heal/Damage column stays), and restores the numbers above 0. **Mobile (2.78.1): the box STACKS** — `html.mobile .hpbox{flex-direction:column}` puts the `.hp-readout` (big Current/Max/Temp numbers) full-width on top via `order:0` and the `.hp-adjust` Heal/amount/Damage controls in a `flex-direction:row` strip beneath (`order:1`). Reason: the desktop side-by-side split (≈94px controls + ~206px readout) starves the readout in the narrow combat card, and `.hp-big` is pinned at `width:3.6ch` — too narrow for a 3-digit value at the 30px readout size, so 152/152/188 clipped against each other and the slash; no font/width tweak fits THREE 3-digit numbers in 206px, so the layout has to change. The mobile rule also widens `.hp-big` to `4.3ch` so 3 digits never clip. The clip is the INPUT's own fixed width vs its content (an `<input>` clips, `scrollWidth>clientWidth`), independent of surrounding space — widening the readout alone doesn't fix it, you must widen the field too. Desktop layout unchanged (rules are `html.mobile`-scoped).

**Max HP is a baseline + modifier/override stack.** Tapping Max (`#hpmax`, now `readonly`) opens the `#hpmax-pop` popover (toggled in the delegated click handler; click-outside closes) with two stepper fields: `#hpmax-mod` (±, adjusts baseline) and `#hpmax-override` (replaces it, wins over the modifier). The **baseline** lives in a hidden `#hpmax-base` — `compute()` writes it from the per-level HP rolls (it no longer writes `#hpmax` directly). `recalcMaxHp()` computes effective = `override ?? base+mod`, writes it into `#hpmax` (so every consumer still reads the effective max there), tints `#hpmax` green (`.hp-mod-up`)/red (`.hp-mod-down`) when it differs from baseline, and shows `(base)` in the `#hpmax-base-disp` span. Legacy/manual sheets with a value in `#hpmax` but no recorded base adopt it as baseline on first recalc; a pre-dialog `overrides.hpmax` pin migrates into the Override field; `hpmax` was removed from `overrideIds()`. `makeSimulacrumData` halves `hpmax-base` and clears mod/override too. The **Long Rest** dialog has a "Reset Max HP changes to baseline" checkbox (`#rest-resetmaxhp`, default on via `restState.resetMaxHp`) — `takeLongRest` clears mod/override and recalcs BEFORE restoring to full, so a reset heals to baseline not the buffed max; toggling it re-renders so the "Restored to full" target updates live. **The ids `#hpcur`/`#hpmax`/`#hptmp` are unchanged** (effective values) — that's what keeps `save()`, `compute()`, `updateDeathSaves()` (death-save row at ≤0), rests (`restHp`), and the Classic overlay sync working; preserve them in any HP rework. New persisted fields are plain `[data-save]` inputs, so they ride `save()`/`applyFields` automatically.

**Input-styling gotcha (bit me repeatedly):** global `input,select,textarea` (≈line 139) AND `body.dark input` (≈line 47) set border+background on every input, and a plain class rule does NOT out-specify the dark one. To make a borderless/box-free number field (the big HP digits) you need `border:none !important; background:transparent !important` on the class PLUS a `body.dark .hp-big{…!important}` override (and for Temp's reveal, a `body.dark .hp-tempin` border reset too). Separately, `input[type=number]{appearance:textfield}` (≈line 145) hides spinners on ALL number inputs — to bring spinner arrows back on one field (`#hp-delta`, `.hp-tempin`) set `appearance:auto` (+ `-moz-appearance:textfield`) and the `::-webkit-*-spin-button{-webkit-appearance:inner-spin-button;appearance:auto}` pseudos. To show arrows only on hover/tap, keep them in layout with `opacity:0` at rest and `opacity:1` on `:hover`/`:focus` (don't toggle `display`, which reflows). Reserve a transparent 1px border at rest so revealing the box doesn't shift neighbors (with `box-sizing:content-box`).
