# D&D Character Sheet

Alex's from-scratch, single-file D&D 5e (2014 rules) character sheet app -- a clean-room replacement for MPMB's PDF sheet, built because MPMB's automation is inseparable from its Adobe/look (reskin proven impossible). The whole app is one self-contained `index.html`: inline CSS + JS, no frameworks, no Adobe or proprietary software required to view it, with the full 5etools sourcebook baked into a `#source-data` `<script>` (~5MB of the ~13MB file) so GitHub Pages serves it self-contained and it works fully offline.

- **GitHub:** `BaesTheorem/dnd-character-sheet` (`main`, origin set, gh auth = BaesTheorem)
- **The app:** `index.html` (~13MB). That's it. Everything ships in this one file.
- **Deploy = push to `main`.** Alex runs the GitHub Pages build (`baestheorem.github.io/dnd-character-sheet`), not the local file or stale Drive/iCloud copies. When he says "I don't see my change," the answer is almost always "reload the Pages tab," not a code bug.

Do NOT transplant into or `cp` over `~/Library/Mobile Documents/.../Character Sheet*.html` (or any of his local copies) as a convenience. The transplant/rescue procedure documented under "Distribution model" is only for when he ASKS for an in-place rescue. Reading his file to reproduce a bug is fine; writing to it is not.

## First moves every session

1. **`grep` on `index.html` WILL hit the baked data blob -- expect it before your first grep, don't get surprised and redirect.** You read this file by grepping constantly, and ~5MB of WotC JSON lives in the `#source-data` `<script>` as ONE physical line (plus base64 at the `PAGES` line). So `grep -n "<term>"` for anything that also appears in the data (`edition`, `bakedBooks`, `name`, `text`, spell/feature names, common words) prints that whole multi-MB line and overflows the tool output (bare `grep -n "edition"` dumped 19MB once). Two habits: (a) **anchor on code-only tokens** that can't be in JSON -- `grep -n "function isBook2024"`, `grep -n "const RULESET_2024"`, `grep -n 'id="loaded-books"'`; (b) when a term might be in the data, **don't print the matched line raw** -- `grep -n "term" index.html | awk -F: '{print $1}'` (line numbers only) or `| cut -c1-160`, then `Read` that line range.
2. **Read `VERSION`** (current SemVer) and the top of the in-app changelog before bumping anything. Alex commits in PARALLEL during sessions -- a stale assumption about the current version will regress it (I once clobbered 2.32.0→2.31.1). Never assume the last value you set is current; re-read first.
3. **For ANY D&D rules value, read the source data -- never use memory.** This is absolute here. My recall of stat blocks, spell dice, level progressions, feature text, DCs, HP formulas has been wrong repeatedly and silently corrupted the sheet (shipped Primal Companion from memory, got passive Perception / HP formula / attack dice / grapple DC all wrong). Pull from `~/My Drive/5etools/data` (override via `FIVETOOLS_DATA`; same path `build-data.py` uses). A server may run at `http://localhost:5050` but is often down -- the raw JSON on disk is always there. Key files: `class/class-<class>.json`, `optionalfeatures.json` (FS:*/EI/MV:B/MM by featureType), `bestiary/bestiary-<src>.json`, `spells/`, `races.json`, `feats.json`, `items.json`, `magicvariants.json`. Strip `{@tag ...}` markup when reading. Verify finished work with a programmatic diff against source when feasible.
4. At the end of every change set, follow **"After every change set" below** -- auto-commit + push, then update THIS skill with anything new you learned.

## Testing protocol (this matters -- read it)

The `<script>`-extract-then-`node --check` syntax check is **UNRELIABLE** on this ~13MB file: a `</script>` literal inside a string truncates the regex extraction (false "Unexpected end of input"); brace-count deltas are noise from strings/regex. A duplicated `function compute(){` once would have shipped a fully-broken sheet and node-on-extracted-script missed it.

**Always verify edits by loading the page in Playwright** and checking `page.on("pageerror")` + `typeof compute === 'function'`. That catches the real breaks. When an Edit looks balanced but the page breaks, `git diff` to spot an accidental duplicated/dropped line (a common cause: an Edit `new_string` that re-includes the trailing context line).

- **`grep` hits the baked data blob** -- see First moves #1 (anchor on code-only tokens, or line-numbers-only / `cut -c1-160`); it's the very first thing to internalize because reading this file means grepping it.

## Keep app CODE copyright-clean (load-bearing constraint)

Alex may one day **sell or more widely distribute the sheet itself**, so the app code must stay free of copyrighted WotC material. The design rule: **the baked `#source-data` blob is the ONLY place copyrighted content is allowed to live.** Null out `#source-data` and what's left should be a copyright-clean app (point it at a 5etools source to reconstitute). The whole-file-with-data-baked-in is fine for Alex's own use *today*; the separation is what keeps a future strip-and-sell viable.

**What this means for every edit that adds content:**
- Never hardcode copyrightable WotC TEXT into app JS (spell/feature/item/invocation/maneuver/metamagic/fighting-style descriptions, stat-block prose). It belongs in `#source-data`, pulled in by a loader. This is already done -- `OPTIONAL_FEATURES` and `FIGHTING_STYLES` text were de-baked into `#source-data` (via `etOptionalFeatures`) so app code is text-free. Keep it that way; don't reintroduce verbatim text into a registry.

App-BEHAVIOR text (UI hints like "Auto-applied to AC when infused") is code copy, not rules text, and stays in code (see the `note` field + `infText()` pattern). FULLY ENFORCED as of 2.135.0 -- the last holdouts were de-baked: `CONDITIONS`/`TCE_RULES`/`SPELL_CHANGES` hold mechanics only. ## Architecture / where things live

- **UNIFIED SOURCE MODEL (`DATA.sources`, shipped 2.85.2→2.86.1) -- read this before touching source loading, merging, or any picker.** All three source-input paths (5etools batch, "Import files", homebrew) are being unified into ONE equal-citizen store `DATA.sources = [{id, name, kind:"5etools"|"file"|"homebrew", enabled, priority, data}]` (`data` = a sheet-schema book object). Helpers near `rebuildFromRaw`: `SRC_KINDS`, `srcId(kind,name)`, `hbBagsToData(hb)` (homebrew lc-keyed bags → book-shaped arrays), `migrateToSources(D)` (folds legacy `_meta.raw` books + `homebrewSources`/`DATA.homebrew` in; run at load), `rebuildFromSources()` (the live merge -- REPLACED all `rebuildFromRaw()` calls; iterates sources by `priority`, `mergeBook` each), `tagSourcesFromRaw(D)` (annotates baked-at-load entities with their source, run at load). **Coexist+tag is the core mechanic:** `mergeBook(into,add,name,opts)` gained `opts.coexistSrc/coexistName/coexist` -- every merged entity is stamped `_src`/`_srcName`; a `_coex` entity (imported/homebrew) keys on `name+src` so a same-name thing from another source COEXISTS (both selectable), a plain entity (official 5etools) keys on `name` so reprints across books still dedup. `hbApplyToData` was rewritten to coexist-merge homebrew structured types (races/feats/backgrounds/subclasses) tagged `_hb+_src+_srcName+_coex` (was: drop-on-official-collision). **Selectors + resolution:** `optLabel(x)` = `"Name · Source"` (ALWAYS shows source, Alex's call) is used by the race/background/feat/spell pickers; `resolveEnt(list,name,src)` resolves a pick to its exact (name,src) entity with name-only fallback. **RACE is wired end-to-end** (the flagship): hidden `#race-src` companion, `data-src` on `#wiz-race-list` buttons, `wizRace()`/`applyRace`/`applyRaceAbilityOnly` resolve by src, wizard commit passes it, edit restores it. **Bake/persist STRIP `DATA.sources`** (`bakeSourceData`/`persistSources` delete it; rebuilt at load) -- do NOT bake it. **ITEM source-choice DONE via a single gate (2.87.0), NOT a map re-key.** Item data lives in ~10 name-keyed maps (`itemText`/`magicItems`/`acItems`/`itemWeights`/`itemSpells`/`magicWeapons`/`spellBonusItems`/`attuneItems`/`itemNames`) -- re-keying all by (name,src) was too high-blast-radius. ### The DATA_VERSION gotcha (causes "Sourcebooks out of date" forever)

When you bump the `DATA_VERSION` const, you **MUST also re-stamp the baked `#source-data` `_meta.dataVersion`** to match. CAREFUL: since 2.85.0 the blob carries MORE THAN ONE `"dataVersion":N` (the top-level `_meta` one, before `"pendingAug"`, is FIRST; per-book raw `_meta` blocks like the baked WGtE carry their own copy later). Re-stamp the FIRST occurrence; a blind replace-ALL also rewrites the book-level copies (harmless today since they match, but verify counts before and after). A const-only bump makes the baked data SELF-STALE; a clobbered stored copy ties-and-wins and the flag shows forever. Because the Edit tool's file-state tracking fights this 13MB file (and SOH `\x01` separators in some sigs can't be matched by Edit at all), use a **verified Python byte-level replace** for these edits, not the Edit tool.

## Themes

There are **two** themes: **Universal Character Sheet** (`ucs`, default, landscape dashboard) and **Classic** (`classic`, WotC PDF overlay). The brand "D&D Beyond" is FULLY SCRUBBED from the app (to avoid treading on the trademark): the old standalone "Universal" theme and the former "D&D Beyond" theme are one theme, displayed AND internally identified as **"Universal Character Sheet"**. There is no `dndbeyond`/`ddb` anywhere except one save-compat migration literal. Don't treat Universal and D&D Beyond as separate options, and don't reintroduce the brand name (UI, comments, or identifiers).

- **A third "Material Design" theme (`material`) was built then REMOVED entirely (2.136.0 → deleted 2.137.2, Alex's call -- he iterated it several times, gold-flat, UCS-clone, neutral surfaces, then dropped it). Do NOT assume it still exists.** Its ONLY code residue: `material` is folded into the legacy-theme migration in `compute()` (≈9759, alongside `universal`/`dndbeyond` → `ucs`) so any character saved with it loads as the Universal sheet -- keep that literal. The two bullets below are the REUSABLE recipe distilled from that work (there's no live third theme to look at now), in case Alex wants another theme later.
- **Adding a new theme (reference recipe):** a theme = (1) a `{id,name}` entry in the `THEMES` array (≈5048), which drives the `#set-theme` dropdown via `renderThemeOptions` (fired on Settings-open, so a new option only appears once settings render -- a Playwright `set-theme` change dispatch on page load sees an EMPTY select; preview by setting `document.body.dataset.theme='<id>'` directly, which is what `applyThemeSetting` does); (2) two CSS blocks `body[data-theme="<id>"]{…light…}` + `body[data-theme="<id>"].dark{…dark…}` defining the vars (`--bg/--card/--ink/--muted/--line/--line2/--accent/--accent-soft/--field/--radius/--shadow/--font`) + signature component styling, placed AFTER the `ucs` palette block (≈1921) so it's past the flat/sharp block in source order. Dark composes automatically (ship both palettes); it's only force-disabled for `classic`. **By default a non-`ucs`/non-`classic` theme renders the CANONICAL portrait page/tab layout** (the DOM mobile uses) -- `wantUcs()` false, all tabs show. **To instead make it a UCS-style landscape dashboard:** the landscape engine is the bottom IIFE gated on `isUcs()` and its layout CSS is `body.ucs-layout` (theme-AGNOSTIC, all `var(--…)`), so broaden `isUcs()` (≈16090) to include the new id (that one change flows through `wantUcs()`/`activate()`/`_ucsSync`/`boot()`; `applyThemeSetting` is IIFE-wrapped to activate/deactivate on switch), define the `--ucs-*` vars in the palette (**only `--ucs-gold` is actually consumed** -- the `#ucs-tabbar .ucs-tab.active` color/border ≈2108; `--ucs-panel`/`--ucs-hp` are defined-but-unused), and make the post-print restore `_ucsAfterPrint` (≈16210) use the live `theme` var, NOT a hardcoded `'ucs'`, or printing the new theme flips it to `ucs` on restore. `beforeprint` deactivates + swaps to the `'universal'` print palette + restores Core cards into `#page-core`, and `TABS`/`syncTabs` are gated on `active()`/`ucs-layout` (not the theme id) -- all shared, so a dashboard clone prints portrait and gets its tab bar for free.
- **The flat/sharp block + how a theme relates to it:** the app-wide taste block (≈1259) is `*{border-radius:0 !important; box-shadow:none !important}` plus `input,select,textarea{background:#fff !important}` and `.ability .mod,.row .total,.passive,.chip,.stat{background:#fff !important; border:1px solid var(--line2) !important}`. - **Conditions & Exhaustion engine:** Defenses is a subsection inside the Combat card (`.combat-sub`), with a **Conditions** subsection beside it. `CONDITIONS` (app-JS registry: key, name, *paraphrased* rules text = copyright-clean, and an `eff` object) + `EXHAUSTION_STAGES` drive everything. `buildConditionsPanel()` (called in `init()` BEFORE `applyAll` so the `data-save` inputs exist to restore) builds `#cond-panel`: one `#cond-<key>` toggle + expandable rules per condition, plus a 6-pip `#exhaustion` tracker. **`#cond-panel` lives in a popup `#cond-modal` (`.modal`/`.open`)**, opened by the "Manage conditions" button; the conditions-sub only shows the active chips + button. `condEffects()` aggregates active conditions + exhaustion into `{disadv:Set, adv:Set, speedZero, speedHalf, hpHalf, incap}` where adv/disadv tags are `attack`/`check`/`save`/`save:str`/`save:dex`/`skill:<key>`. A condition's `eff.disadv`/`eff.adv` accept ANY of those target strings (e.g. Blinded is `disadv:['attack','skill:perception']` -- the `skill:perception` tag both draws the red-D on the Perception line AND feeds the passive-Perception penalty, wired 2.118.0); `eff.autofail:['str','dex']` folds to `save:str`/`save:dex` disadv. Auto-applied in `compute()`: **speed** (the `#speed` write applies `conditionSpeed()` → 0 or half), **HP max** (`recalcMaxHp()` halves on exhaustion ≥4, reading `exhaustionLevel()` directly -- the aggregated `hpHalf` flag is currently unused/dead but harmless; `incap` is informational-only by design, not consumed anywhere), **passive Perception ±5** (RAW: advantage/disadvantage on the Perception check shifts it; `compute()` reads `condEffects()` for adv/disadv on `check` or `skill:perception` -- NOT `gatherAdvSources()`, to exclude situational FEATURE advantages like Dungeon Delver -- so Blinded/Frightened/Poisoned/exhaustion≥1 each give −5), and **adv/disadv markers** via `renderConditionMarks()` (MUST run last in compute, after roll values are written) -- `setAdvMark(box,…)` pins a green-A/red-D d20 (`advIconSvg()`, inline SVG) as an absolute corner badge (`.advmark` + `.advmark-host`) on the upper-right of each value's box -- the skill/save total boxes (`#sktot-*`/`#savetot-*`), the Initiative `.stat`, and each filled attack row's Bonus `<td>`. `compute()` rewrites the total's textContent so the badge is re-appended each pass (hence renderConditionMarks runs last). `advFor()` cancels when both adv & disadv apply. `renderConditions()` paints the active-chip row + panel state. **Feature-granted adv/disadv:** `featureAdvEntries()` detects, from race / class+level / Features text / equipped armor, advantages & disadvantages on specific rolls (e.g. Barbarian Rage, Gnome Cunning, armor Stealth penalty). `gatherAdvSources()` merges condition + feature sources into a `target → [{kind,note}]` map (targets now include `skill:<key>`); `resolveAdv(map, keys)` cancels adv-vs-disadv and joins the situational notes for the tooltip. **To wire a new feature/feat/spell, add one entry to `featureAdvEntries()`** -- `{kind:'adv'|'disadv', targets:['skill:stealth'|'save:wis'|'check'|'attack'|…], note:'when it applies'}` -- and it flows through automatically. Most feature advantages are conditional, so the note states the condition (the marker is a reminder). Rules sourced from 5etools `conditionsdiseases.json` (PHB), paraphrased.
- **Defenses render as COMPUTED CHIPS too (2.124.0), same treatment as Senses -- see the dedicated Defenses-chips bullet below; the "`#defnotes` is add-only, never live-injected" framing here is now PARTLY SUPERSEDED** (`scanDefenses` still writes the box at build, but `renderDefenseChips()` recomputes the derivable lines live into `#def-chips` and STRIPS them from the box each `compute()`). **`scanDefenses(text)` is a SEPARATE prose-scanner** (≈line 3299, distinct from `featureAdvEntries()`): it regex-pulls resistances/immunities and granted (dis)advantages out of feature text into short lines, spliced into the editable `#defnotes` box **once at character creation/Edit** (line ~10535) and then persisted. It does NOT rebuild each `compute()`, so a stale/bad line stays in a saved character until the user deletes it by hand. The recurring trap: feature prose where "you have advantage" is a *condition*, not a *grant* (Sneak Attack: "...**if** you have advantage on the attack roll"; Assassinate; "...you don't have disadvantage...") -- the scanner used to misread these and emit a garbled "Adv. on the attacks". Guard added: a `condAdv` test skips the four adv/disadv branches when the clause is governed by if/when/unless/whether/provided/even-if/so-long-as + "you have/gain (dis)advantage". `_tidyAdvMid` also now strips a lone article (`/^(?:an?|the)\b\s*/`) so a bare "the attack rolls" renders as "attacks", not "the attacks". General lesson: if a trait states a (dis)advantage that's gated behind a *mode/option choice within that trait* (not an if/when clause `condAdv` catches), exclude that trait from the scrape and handle the conditional live instead. ## Homebrew Builder (the three-step workflow for fully fleshing out homebrew)

When Alex wants to create homebrew material (a spell, item, and eventually a feat/race/subclass/class/background), drive it through these THREE steps in order. The point is that the finished piece ends up as a portable JSON file that, when imported, gets **first-class mechanical support** on the sheet (auto-applied AC/attack/DC/attunement/etc.), not just stored as inert text.

**Step 1 -- Iterate on the material itself, together.** Design it WITH Alex before touching code. Settle the name, the rules text, and (critically) the *mechanics*: what numbers/effects it grants and under what conditions. Ground every rules value in real D&D data (`~/My Drive/5etools/data`) per the absolute "never from memory" rule at the top of this skill. Decide the balance/tier. The deliverable of this step is an agreed spec: exactly what the thing does, in mechanical terms.

**Step 2 -- Modify the sheet code to support its mechanics (only if needed).** Check whether the existing homebrew schema + engines already cover the mechanics:
  - A plain **spell** (level/school/components/text/higher) or a **magic item** whose effects are AC bonus / spell-attack bonus / spell-save-DC bonus / attunement / weapon math (Ancestral Weapon) -- **no code change needed.** The current homebrew item/spell shapes + the existing overlay functions (`hbActiveItems`/`hbActiveSpells`/`hbEnabledItem`/`acItemMap`/`spellBonusItemMap`/`attuneSet`/`allItemText`, and `awDerive`/`hbAwMagicWeapon` for AW) already auto-apply these. Skip to step 3.
  - A mechanic **beyond** that (a novel rider, a new resource, a feat that grants a skill/attack, a race trait with a special AC formula, etc.) -- extend the sheet using the **proven injection recipe** (the same one items + AW follow): store the new field on the per-source object, add/extend a normalizer, and inject an `hbActive<Type>()` (or new field handler) **at that mechanic's resolver read points** -- NEVER merge homebrew into `DATA`/`mergeBook` (homebrew is a carried key, not a merged book). For copyright cleanliness, names+mechanics+formulas stay in app JS; verbatim copyrighted TEXT rides `#source-data` (see "Keep app CODE copyright-clean"). Bump SemVer for the code change.

**Step 3 -- Encode it as a homebrew JSON file for first-class import.** Author the finished material as a homebrew JSON envelope and import it via the Homebrew Studio's **"Import JSON…"** button (it merges into the *currently selected* source). Because import routes each entry through the same normalizer + storage as the in-app forms, the imported content gets identical first-class treatment. The envelope (shipped 2.67.0):
```json
{
  "_meta": { "homebrew": true, "name": "Source name (optional)" },
  "spells": [ { "name":"…", "level":2, "school":"Evocation", "components":"VS",
               "time":"1 action", "range":"60 feet", "duration":"Instantaneous",
               "material":"", "conc":true, "ritual":false, "text":"…", "higher":"…" } ],
  "items":  [ { "name":"…", "type":"Wondrous Item", "rarity":"Rare", "attune":true,
               "acBonus":0, "spellAtk":0, "spellDc":0, "text":"…",
               "aw":{ … } } ]
}
```
Each content type accepts an **array OR an object map** (`{lowercase-name: obj}`); merge is additive, by lowercased name, last-wins. `components` tolerates 5etools-style `{v,s,m}` (normalized to a `"VSM"` string). An `items[].aw` blob (Ancestral Weapon build) is preserved and round-trips; if present, an **export** also bundles the AW upgrade catalog + text so the file is self-contained. A full **sourcebook**-schema file (`races`/`classes`/`spells` as top-level arrays) is rejected here with a pointer to Settings → Import files… -- don't conflate the two import paths.

**Code seam (all ≈ the `importAwContent` neighborhood, before `buildHbStudio`):** `HB_IMPORT_TYPES` is the **single registry** of homebrew content types -- `[{key, label, norm}]`, currently `spells` + `items`. `normHbSpell`/`normHbItem` coerce a loose object into the stored shape. `hbImportIntoSource(idx, d)` merges a parsed file into `homebrewSources[idx]` (returns `{counts, total, name}` or `{err}`); `hbExportSource(idx)` writes the selected source out (`download`). `hbAwBundleInto(d)` folds AW upgrade defs+text and is shared by `importAwContent` + the homebrew importer (DRY -- don't reintroduce a second copy). ## Self-heal & migrations (index)

Central map of everything that REPAIRS a broken/starved file or MUTATES source/character data at runtime. Details live in the linked sections; this is the "what fires when" table so a future session doesn't rediscover them. **Before adding another heal/migration, check here first -- several of these have overlapping trigger conditions and a naive addition can double-fire or fight an existing one.** General lessons that recur across all of them: (1) a fix that runs in the BROKEN build's own code can't rescue that build -- the repair must ride the DOWNLOADED build and run on OPEN (the SW-wedge / starved-data lesson); (2) bake/update paths must base merges on the EXISTING baked blob, never stringify a possibly-empty runtime map forward, or they self-perpetuate a clobber; (3) most heals are idempotent + persist via a trailing `save()` -- keep them so.

## Distribution model

**Saved copies serialize the LIVE DOM; runtime-built chrome must be stripped or it ships as a dead corpse (2.93.1).** `btn-savecopy` and `shareBlankSheet` serialize `document.documentElement.cloneNode(true)`, so any lazily-built, listener-wired element that exists at save time rides into the file as markup with ZERO listeners (listeners never serialize). The killer combo is an existence-guarded builder: `buildHbStudio`'s old `if($("hb-studio")) return` saw the corpse on next open, skipped the rebuild, and the user got an unresponsive modal they couldn't even close (Alex hit exactly this: he'd opened the Studio, saved a copy, and the copy's Studio was dead). Fixes shipped: (a) every runtime-appended element (both builders, notice/confirm modal, prep overlay, feat detail, ctx menu, cast pop, install-hint bar, prep float, preview-card pop) sets `el.dataset.transient="1"` at creation and `stripTransientChrome(clone)` removes `[data-transient]` in BOTH clone-download paths; (b) the two guarded builders (`buildHbStudio`, `buildAwBuilder`) self-heal: at build they set the JS property `m._live=true` (properties don't serialize), and the guard is now "exists && `_live` → return; exists without `_live` → it's a corpse, `remove()` and rebuild," so files saved by OLDER builds recover on open with new code. When adding ANY new lazily-built body chrome: tag it `data-transient`; if it has an existence guard, use the `_live` corpse-heal idiom. Static-HTML modals (`#settings`, `#cond-modal`, `#hpmax-pop`, the banners) are re-wired at init every load and are safe to serialize; do NOT strip them. Diagnostic signature for this bug class: buttons dead in a SAVED file only, zero console errors, and a synthetic `el.click()` also does nothing (listener never attached), while calling the close fn directly works; confirm by grepping the file for a literal `id="hb-studio"` in the static HTML (a healthy build has zero: that id only ever exists via JS property assignment). Note `updateApp`'s downloaded-update path parses the FETCHED document, so it never carried corpses; only Save-copy/blank-share did. An already-corpsed file runs its own old code, so it can't self-heal until updated: rescue by cutting the corpse div(s) out of the file tail (they sit after the last `</script>`; back up first), which preserves the baked characters/homebrew exactly. **Rescue-by-`cp` caveat (supersedes the bare "cp a good build over it" advice): a file that carries baked characters partitions its storage by `BASE_KEY = "dnd-sheet-file-" + hash(embedded-data payload)` (≈2998; savedAt/portrait/contentHash excluded from the hash). The clean repo build has `embedded-data: null` → `BASE_KEY = "dnd-sheet-2014-v1"` (the main library), so a raw `cp` silently switches the user to a DIFFERENT character store and their recent edits "vanish." The safe in-place update is a TRANSPLANT: take the fresh build and splice in the target file's five data blocks: `#source-data`, `#embedded-data`, `#embedded-roster`, `#embedded-prefs`, `#embedded-template-id` -- verbatim (Python regex on the `<script id=...>` bodies). Identical embedded-data bytes → identical BASE_KEY → seamless partition continuity; verify by comparing `BASE_KEY` between the pre-transplant backup and the result IN THE SAME RUN (never assert a hardcoded historical key value across sessions -- `BASE_KEY` is a content hash of the baked roster, so if the file's roster ever changed the absolute key legitimately differs; only the pre-vs-post equality matters). **The stronger, decision-relevant invariant is that all characters LOAD, and baked characters load from the `embedded-roster` regardless of partition** (so a key change strands only UNBAKED live edits, never the baked roster). Verify by opening the result in a CLEAN storage context (`browser.new_context()`, empty partition) and counting `#charmgr .cm-card` = the expected roster size; if they all show, the file is safe to hand back whatever the key computes to. A user blob being much smaller than the repo blob is NORMAL (user bakes lack never-loaded books' raw blocks), not starvation -- judge by spell count/dataVersion.**

**Updates refresh SOURCE DATA additively, not just the app code (2.99.0). `mergeUpdatedSources` now routes through `additiveMergeSources(user, fresh)` (both ≈13525).** The old function had a size-heuristic branch (`_ver` tie && `_size(user) >= _size(shipped)` → keep user whole) that SILENTLY SKIPPED genuinely-new entries whenever the user had more TOTAL content than the shipped build (e.g. a personal file with extra adventures loaded) -- so a build that added a few spells within an existing book never reached that user. `additiveMergeSources` folds the fresh build's content INTO the user's data: per collection (spells/races/items/monsters/maps), entries the user LACKS are added and an OFFICIAL entry whose **normalized content hash differs is refreshed** to the fresh version (errata / new-within-a-book). The hash (`stable(v)`: recursive key-sorted JSON) **strips runtime-only annotations (keys starting with `_`: `_src`/`_srcName`/`_coex`/`_hb`)** so re-tagging at load isn't read as a change; **`_hb` (homebrew-injected) entries are never overwritten**; the user's UNIQUE content (loaded adventures, imports the build doesn't ship) + `homebrew` are preserved verbatim; `_meta` books/bakedBooks/raw/fiveE are unioned (a new fresh book inherits its default enabled/disabled state); `dataVersion=max`; awText = fresh fills gaps, user/imported wins. Because the full shipped baseline is always folded in, this ALSO heals a starved dataset in one pass -- it REPLACES the old starvation `_size` branch (keyOf is NAME-only, lowercased). The only kept guard is `_ver(user) > _ver(shipped)` → keep user whole (don't downgrade a strictly-newer build). **Both update surfaces route through it:** the local-file download via `bakeAllInto`→`mergeUpdatedSources` (already there), and `updateApp`'s HOSTED branch now parses the streamed fresh `#source-data`, `mergeUpdatedSources(freshSD, DATA)`, sets `DATA` + `persistSources()` BEFORE `location.reload()` (the reload boots from the merged `SOURCES_KEY` union) -- hosted used to just reload and reuse persisted sources untouched. **The service worker (`sw.js`) is self-healing as of 2.80.0 -- a stale/broken cache can NEVER strand a hosted/Pages user, and users never run code or reload by hand. ## HP widget (Combat card)

The Combat card's HP block is the compact `.hpbox` widget, modeled on D&D Beyond: `Heal`/`Damage` buttons (`#hp-heal`/`#hp-damage`) around a number field (`#hp-delta`) on the left, big `Current / Max` digits centered with `Temp` right beside Max, and a `.hp-head` header above the box. Capped at `max-width:460px` so it reads as a small card, not a full-width bar (the combat card spans the whole top band in the landscape layout). `applyHpDelta(heal)` does the math: Damage absorbs into Temp HP first (5e RAW) then Current (floored at 0); Heal adds to Current capped at Max and NEVER touches Temp; the delta clears after applying so a stray double-click can't silently re-apply. **Current can never exceed Max** -- `onChange` clamps `#hpcur` to `#hpmax`, and `recalcMaxHp()` re-clamps it whenever Max changes. **Temp (`#hptmp`) is uncapped** (floored at 0 via `min="0"`); it reads as a plain muted number but tap/hover reveals a bordered stepper box (CSS-only `:hover`/`:focus` reveal, no JS). The `.deathsaves` row lives INSIDE `.hp-readout` now: `updateDeathSaves()` hides `.hp-vals` and shows the death saves in its place at ≤0 HP (Heal/Damage column stays), and restores the numbers above 0. **Mobile (2.78.1): the box STACKS** -- `html.mobile .hpbox{flex-direction:column}` puts the `.hp-readout` (big Current/Max/Temp numbers) full-width on top via `order:0` and the `.hp-adjust` Heal/amount/Damage controls in a `flex-direction:row` strip beneath (`order:1`). Reason: the desktop side-by-side split (≈94px controls + ~206px readout) starves the readout in the narrow combat card, and `.hp-big` is pinned at `width:3.6ch` -- too narrow for a 3-digit value at the 30px readout size, so 152/152/188 clipped against each other and the slash; no font/width tweak fits THREE 3-digit numbers in 206px, so the layout has to change. The mobile rule also widens `.hp-big` to `4.3ch` so 3 digits never clip. The clip is the INPUT's own fixed width vs its content (an `<input>` clips, `scrollWidth>clientWidth`), independent of surrounding space -- widening the readout alone doesn't fix it, you must widen the field too. Desktop layout unchanged (rules are `html.mobile`-scoped).

**Max HP is a baseline + modifier/override stack.** Tapping Max (`#hpmax`, now `readonly`) opens the `#hpmax-pop` popover (toggled in the delegated click handler; click-outside closes) with two stepper fields: `#hpmax-mod` (±, adjusts baseline) and `#hpmax-override` (replaces it, wins over the modifier). Legacy/manual sheets with a value in `#hpmax` but no recorded base adopt it as baseline on first recalc; a pre-dialog `overrides.hpmax` pin migrates into the Override field; `hpmax` was removed from `overrideIds()`. `makeSimulacrumData` halves `hpmax-base` and clears mod/override too. The **Long Rest** dialog has a "Reset Max HP changes to baseline" checkbox (`#rest-resetmaxhp`, default on via `restState.resetMaxHp`) -- `takeLongRest` clears mod/override and recalcs BEFORE restoring to full, so a reset heals to baseline not the buffed max; toggling it re-renders so the "Restored to full" target updates live. **The ids `#hpcur`/`#hpmax`/`#hptmp` are unchanged** (effective values) -- that's what keeps `save()`, `compute()`, `updateDeathSaves()` (death-save row at ≤0), rests (`restHp`), and the Classic overlay sync working; preserve them in any HP rework. **Input-styling gotcha (bit me repeatedly):** global `input,select,textarea` (≈line 139) AND `body.dark input` (≈line 47) set border+background on every input, and a plain class rule does NOT out-specify the dark one. To make a borderless/box-free number field (the big HP digits) you need `border:none !important; background:transparent !important` on the class PLUS a `body.dark .hp-big{…!important}` override (and for Temp's reveal, a `body.dark .hp-tempin` border reset too). Separately, `input[type=number]{appearance:textfield}` (≈line 145) hides spinners on ALL number inputs -- to bring spinner arrows back on one field (`#hp-delta`, `.hp-tempin`) set `appearance:auto` (+ `-moz-appearance:textfield`) and the `::-webkit-*-spin-button{-webkit-appearance:inner-spin-button;appearance:auto}` pseudos. To show arrows only on hover/tap, keep them in layout with `opacity:0` at rest and `opacity:1` on `:hover`/`:focus` (don't toggle `display`, which reflows). Reserve a transparent 1px border at rest so revealing the box doesn't shift neighbors (with `box-sizing:content-box`). **BUT a webkit spinner at `opacity:0` still RESERVES its ~9px of layout width on the RIGHT of the field, so a `text-align:center` value/placeholder centers in the reduced (left) content area and renders visibly LEFT of the field's true center (bit the Temp box: the `#hptmp` box was centered under the TEMP label, yet the "--" sat left of it -- fixed 2.116.5).** When the RESTING centered look must line up under a label, drop the reserved space at rest with `appearance:textfield; -webkit-appearance:textfield` on the field and restore `appearance:auto; -webkit-appearance:auto` on `:hover`/`:focus` so the stepper returns (the opacity-toggle pattern alone can't fix it -- the space is reserved regardless of the pseudo's opacity). **BUT `appearance:textfield` on the INPUT is NOT enough if a `::-webkit-inner-spin-button` rule sets `-webkit-appearance:inner-spin-button` -- that pseudo re-materializes the spinner (and re-reserves its width) even against the input's textfield appearance. That exact incomplete fix shipped as 2.116.5 and the "--" was STILL offset (Alex re-reported it); 2.122.1 finished it: at rest the pseudo must be `-webkit-appearance:none; appearance:none; margin:0` (spinner truly gone, zero reserved width), and the stepper is brought back ONLY on `:hover`/`:focus` via `.hp-tempin:hover::-webkit-inner-spin-button{-webkit-appearance:inner-spin-button; appearance:auto; opacity:1}` (plus the input's `appearance:auto` on hover). So the resting spinner-hide lives on the PSEUDO (`appearance:none`), not just the input; `opacity:0` on the pseudo is the wrong tool (keeps the width).** Verify centering with a rendered SCREENSHOT (crop `.hpbox`), not `getBoundingClientRect` -- the box rect is already centered (its center == the label center, e.g. both 406.2), only the painted glyphs are off, so a rect probe reports "centered" while the eye sees the offset. TWO MORE rules feed this gotcha (found fixing the Speed box, 2.92.0): the flat/sharp block (≈1134) forces `input{background:#fff !important}` and `input:focus{outline:none !important}`, and `body[data-theme="ucs"] input` (≈1746) adds `border:1px solid var(--line)` at (0,1,2) specificity, which BEATS `.stat input` (0,1,1) -- so any "make this input look like a plain value" fix needs `border:none !important; background:transparent !important` on a ≥(0,2,2) selector PLUS the `body.dark` twin (the `.combat-top .stat input` rule ≈396 is the template). Non-text controls (buttons/tabs/checkboxes) get keyboard focus from one `:focus-visible` outline rule in the flat/sharp block (2.92.0) -- keep it when touching that block.

- **"The mobile view scrolls left into empty space / graphical glitches" = the sticky `.pagetabs` overscroll (fixed 2.88.1).** `html.mobile .pagetabs` (CSS ≈1345) is `position:sticky; overflow-x:auto` with a `margin:0 -10px` edge-bleed so the swipeable tab strip reaches the screen edges. On a REAL iPhone that negative-margin overhang lets Safari rubber-band the whole document sideways into the blank -10px region (empty space + sticky-repaint glitches). **You cannot reproduce this headlessly** -- Chromium AND authentic iPhone-13 WebKit (Playwright `p.devices["iPhone 13"]` + `p.webkit`) both report `maxScrollX:0` / `documentElement.scrollWidth == innerWidth` even under simulated tab-swipe/modal/every-page interaction; it's a real-device touch-momentum behavior. Fix = `html.mobile, html.mobile body{ overflow-x:clip; }` (≈1327). **Use `overflow-x:clip`, NOT `hidden`** -- `clip` does not create a scroll container, so it leaves `position:sticky` (the pinned tab bar) and vertical document scrolling intact; `hidden` would break them. Verified on iPhone-13 WebKit: no h-scroll, tab bar still scrolls internally + stays pinned (`top:0` after a vertical scroll), page scrolls vertically. General lesson: for a "phantom sideways scroll on iPhone only" report, suspect a sticky/negative-margin/`overflow-x` element and reach for `overflow-x:clip` on the mobile document rather than chasing a headless repro.
